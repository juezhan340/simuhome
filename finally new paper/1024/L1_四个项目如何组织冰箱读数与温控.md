# L1 四个项目如何组织冰箱读数与温控

本文只讨论一个问题：

```text
同一台冰箱内部
  冷藏当前温度
  冷冻当前温度
  冷藏目标温度
  冷冻目标温度
到底应该怎样组织
```

范围只包括冰箱这个 Device 内部的信息：

```text
纳入
  冰箱本体的状态
  冷藏、冷冻等功能分区
  内部温度读数
  内部目标温度
  内部温区控制入口

不纳入
  客厅独立温湿度传感器
  房间光照传感器
  PM2.5 传感器
  门窗、人体移动等家庭环境传感器
  室外天气
```

这里不讨论具体温度应该调到多少，而是检查四个对象怎样在冰箱目录内部安排物理设备、温区、状态、读数和控制入口：

```text
PersonalHomeBench
SMH-Bench
SimuHome
Miloco
```

## 0 先给结论

四个对象对“一台冰箱”给出的边界并不相同：

```text
PersonalHomeBench
  家庭层有 appliances 和 sensors 两个集合
  本次不把冰箱内部温度当作独立 SensorObject
  冰箱内部状态应落在 ApplianceObject 的 appliance state / feature 范围

SMH-Bench
  家庭层只有 devices
  冰箱是一台 Device
  冷藏和冷冻可以作为两个 Component
  当前温度是 Attribute
  目标温度是 Attribute
  修改目标温度通过 Service

SimuHome
  论文和当前代码把 Refrigerator 与 Freezer 拆成两个逻辑 Device
  每个逻辑 Device 内都有 Temperature Measurement
  和 Temperature Control
  这种实现更接近“两个温区设备”，不是“一台整机两个温区”

Miloco
  一台 MIoT Device
  fridge 服务表示整机
  fridge-chamber 服务表示温区
  当前温度和 target-temperature 都是温区服务里的 Property
  多个温区由不同的 siid 区分
```

把冷藏和冷冻四个值拆开看：

```text
冷藏当前温度
  可观测状态

冷冻当前温度
  可观测状态

冷藏目标温度
  可读状态 + 可写目标

冷冻目标温度
  可读状态 + 可写目标
```

“当前温度”和“目标温度”是两种状态语义。“只读”和“可写”是实现上的访问属性。两者不能混成一个维度。

## 1 四个项目的共同问题

一台智能冰箱至少包含四层信息：

```text
物理身份
  这是厨房里的哪一台冰箱

功能分区
  冷藏区、冷冻区，部分设备还有变温区

状态
  每个温区当前的测量温度
  每个温区当前的目标温度

动作
  修改某个温区的目标温度
```

理想情况下，可以写成：

```text
Device
└─ refrigerator
   ├─ desc: 双温区冰箱
   ├─ zone: fresh
   │  ├─ observe: current_temperature
   │  ├─ control: set_target_temperature
   │  └─ readback: target_temperature
   └─ zone: freezer
      ├─ observe: current_temperature
      ├─ control: set_target_temperature
      └─ readback: target_temperature
```

四个项目并非都采用这个结构。它们分别在家庭对象、设备、逻辑设备和协议服务四个层级上选择了不同的切分方式。

## 2 PersonalHomeBench

### 2.1 为什么本次把冰箱内部温度收在 ApplianceObject

PersonalHomeBench 的 Household schema 确实有两个并列集合：

```text
Household
├─ appliances[]
│  ├─ appliance: ApplianceObject
│  └─ location
├─ sensors[]
│  ├─ sensor: SensorObject
│  └─ location
├─ members[]
├─ memories[]
└─ context
```

本次只研究冰箱内部，因此 `sensors[]` 不属于主要分析对象。论文中的工具和示例进一步表明，这个集合主要面向家庭里的独立传感器和家庭环境信息：

```text
get_owned_sensors
get_sensors
get_sensors_by_location
get_appliance_and_sensor_events
```

公开附录里的传感器相关例子包括：

```text
漏水状态
门磁开关状态
人体移动状态
传感器离线或故障
室内温度、湿度、灰尘、气味等环境上下文
```

论文没有把这些家庭级传感器描述成“冰箱内部温度的上位容器”。

从工具职责看，冰箱内部状态有另一条明确通道：

```text
get_owned_appliances()
  List appliances

get_appliances(appliance_names)
  Returns detailed state information for specified appliances

update_appliance(appliance_name, state)
  Updates the appliance state

get_appliance_features(appliance_names)
  Lists supported appliance features and parameters

run_appliance_feature(...)
  Executes an appliance feature
```

因此本研究采用以下判断：

```text
冰箱本体
  appliances[].ApplianceObject

冰箱内部读数与设定
  留在 ApplianceObject 内部
  不提升为家庭层 sensors[]

客厅温湿度、光照、PM2.5、门磁、人体移动
  才属于本次不纳入的外部传感器范畴
```

这个判断有一个证据边界：

```text
论文明确
  get_appliances 返回家电详细状态
  update_appliance 更新家电状态
  appliance feature 负责设备能力发现与执行

论文未展开
  ApplianceObject 的具体对象字段
  冰箱 state 中温度字段的精确名称
  是否使用 cold / freezer / zone / compartment 等命名
```

### 2.2 冰箱内部应怎样落到 ApplianceObject

只考虑冰箱目录内部，最符合论文工具职责的结构是：

```text
Household
└─ appliances[]
   └─ refrigerator_01: ApplianceObject
      ├─ identity / metadata
      │  ├─ appliance name
      │  └─ location = kitchen
      │
      ├─ state
      │  ├─ fresh zone
      │  │  ├─ current_temperature
      │  │  └─ target_temperature
      │  └─ freezer zone
      │     ├─ current_temperature
      │     └─ target_temperature
      │
      └─ features
         ├─ set fresh zone target temperature
         └─ set freezer zone target temperature
```

上面的字段形状是解释结构。论文只公开了 `ApplianceObject` 类型名，没有公开它的完整字段定义，所以这里不能把 `current_temperature`、`target_temperature` 写成已经确认的官方字段名。

本 L1 采用的对象归属是：

```text
四个温度值属于 refrigerator_01
不属于 Household.sensors[] 下另一台独立对象
```

### 2.3 冰箱 feature 接口公开了什么

PersonalHomeTools 提供：

```text
get_owned_appliances()
get_appliances(...)
get_appliance_features(...)
run_appliance_feature(...)
```

这台冰箱在论文附录里的 feature 表是：

```text
refrigerator
├─ view_contents
├─ update_display_widgets
├─ check_inventory
├─ recommend_recipe
├─ fridge_diagnostics
└─ control_ice_maker
```

这张表没有列出：

```text
读取冷藏当前温度
读取冷冻当前温度
设置冷藏目标温度
设置冷冻目标温度
```

所以 PersonalHomeBench 在这四个温度值上有两层证据缺口：

```text
设备归属
  可以由 ApplianceObject 的 detailed state 和 feature 体系解释

精确接口
  公开的 refrigerator feature 表没有温度读取和温度设置项
  不能据此编造官方 temperature feature 名称、参数或返回结构
```

这并不阻碍对象建模，但会影响“逐字段复刻 PersonalHomeBench”的确定性。

### 2.4 它的冰箱内部组织特点

```text
家庭层
  appliances[] 与 sensors[] 分开

进入冰箱目录后
  冷藏与冷冻状态应收在 ApplianceObject 内部

能力面
  state 返回详细设备状态
  feature 负责能力发现与控制
```

它的内部特点：

```text
外部传感器不会污染冰箱能力目录
冰箱本体仍是 appliances[] 下的一个家电对象
温区是冰箱内部概念，不是家庭顶层对象
设备状态查询与 feature 执行分开
```

仍需补的规格：

```text
ApplianceObject.state 的完整字段
冷藏、冷冻温区的统一命名
温度设定 feature 的官方名称、参数、范围和读回关系
```

### 2.5 工具参数与执行例子

参数卡：

```text
get_appliance_features
  appliance_names: list[str]              ["kitchen refrigerator"]

run_appliance_feature
  appliance_name: str                     "kitchen refrigerator"
  feature_method: str                     "fridge_diagnostics"
  feature_kwargs: dict                    {}
```

一次完整调用：

```json
{
  "name": "run_appliance_feature",
  "arguments": {
    "appliance_name": "kitchen refrigerator",
    "feature_method": "fridge_diagnostics",
    "feature_kwargs": {}
  }
}
```

```text
返回
  冰箱诊断信息，例如门未关、通信异常或未发现已知问题

状态变化
  诊断通常只读
```

如果 feature 需要参数，参数全部放进 `feature_kwargs`：

```text
get_appliance_features()
  → 返回该 feature 的参数名和类型
  → 按返回结构填写 feature_kwargs
```

论文公开的冰箱 feature 表没有温度设置项，因此不能虚构官方温度参数。可确认的工具固定为三个外层参数：两个字符串和一个字典。
## 3 SMH-Bench

### 3.1 家庭层只有 rooms 与 devices

SMH-Bench 的 HomeEnv 顶层结构是：

```text
Home
├─ rooms[]
└─ devices[]
```

论文明确将 Device 定义为：

```text
controllable or observable entity
```

独立温湿度、人体移动等传感器如果在家庭层单独寻址，也会成为 `category=sensor` 的 Device。这类外部传感器本次不纳入。

本文只看 `kitchen_refrigerator` 这个 Device 的目录内部，因此继续使用：

```text
Device
├─ attributes
├─ services
├─ components
└─ userdata
```

### 3.2 用 Component 表达冷藏与冷冻

SMH-Bench 论文没有给出冰箱 JSON。按它公开的 schema，最自然的组织是：

```text
Device
└─ kitchen_refrigerator
   ├─ userdata
   │  ├─ did: fridge_01
   │  ├─ category: refrigerator
   │  └─ room: kitchen
   │
   ├─ description
   │  └─ 双温区冰箱，可查看和设置冷藏、冷冻温度
   │
   ├─ components
   │  ├─ fresh
   │  │  ├─ attributes
   │  │  │  ├─ current_temperature
   │  │  │  └─ target_temperature
   │  │  └─ services
   │  │     └─ set_target_temperature
   │  │
   │  └─ freezer
   │     ├─ attributes
   │     │  ├─ current_temperature
   │     │  └─ target_temperature
   │     └─ services
   │        └─ set_target_temperature
   │
   └─ device-level attributes / services
      ├─ door_state
      ├─ fault_state
      └─ ...
```

四个值分别落在：

```text
fresh.current_temperature
fresh.target_temperature
freezer.current_temperature
freezer.target_temperature
```

控制入口分别落在：

```text
fresh.set_target_temperature(value)
freezer.set_target_temperature(value)
```

### 3.3 读写差异如何形成

SMH-Bench 的 Attribute schema 没有直接提供 `readable` 和 `writable` 字段。它通过对象行为形成读写差异：

```text
Attribute
  保存类型化状态和当前值

Service
  是经过验证的状态转换
  只允许通过 Service 修改状态
```

因此可以推导：

```text
current_temperature
  没有 set_current_temperature Service
  对 agent 表现为只读观测

target_temperature
  有 set_target_temperature Service
  对 agent 表现为可读、可通过 Service 更新的状态
```

这里的关键不是把 `current_temperature` 和 `target_temperature` 放到两个不同对象中。它们都是 Attribute，差异来自是否存在一个能修改它的 Service。

### 3.4 它的组织特点

```text
物理设备
  一台冰箱

功能分区
  fresh / freezer Component

观测与状态
  Component 内 Attribute

控制
  Component 内 Service

名称消歧
  fresh.* / freezer.* 命名空间
```

这套结构最适合回答“同一个设备里同时存在只读状态和可操作能力时怎么放”。

### 3.5 工具参数与执行例子：三工具与冰箱调温

Environment-Interactive Agent 模型启动时只看到三个工具：

| 工具 | 用途 | 参数名与冰箱示例 |
|---|---|---|
| `query_device` | 查找设备、能力和状态 | `what`、`did`、`room`、`tags`；例：`{"what":"spec_status","did":"fridge_101"}` |
| `control_device` | 立即执行服务 | `did`、`locator`、`arguments`；例：`{"did":"fridge_101","locator":"fresh.set_target_temperature","arguments":{"temperature":5}}` |
| `create_automation` | 创建定时或条件触发规则 | `conditions.time_cron`、`conditions.state_expr`、`actions[]` |

`query_device.what` 的四种填法：

| `what` | 用途 | 冰箱示例 |
|---|---|---|
| `brief` | 查候选设备 | `{"what":"brief","room":"kitchen","tags":"refrigerator"}` |
| `spec` | 查能力与参数 | `{"what":"spec","did":"fridge_101"}` |
| `status` | 查当前状态 | `{"what":"status","did":"fridge_101"}` |
| `spec_status` | 同时查能力与状态 | `{"what":"spec_status","did":"fridge_101"}` |

完整调温链：

```text
USER
  把厨房冰箱冷藏室目标温度设置为 5°C
       ↓
MODEL → query_device
  {"what":"spec_status","did":"fridge_101"}
       ↓
TOOL
  fresh.current_temperature = 4
  fresh.target_temperature = 6
  service = fresh.set_target_temperature(temperature:number)
       ↓
MODEL → control_device
  {"did":"fridge_101",
   "locator":"fresh.set_target_temperature",
   "arguments":{"temperature":5}}
       ↓
TOOL
  ok = true
  fresh.target_temperature: 6 -> 5
       ↓
MODEL
  已将厨房冰箱冷藏室目标温度设置为 5°C
```

如果设备确实要求先开机，在 `control_device` 前增加
`{"did":"fridge_101","locator":"turn_on","arguments":{}}`。

`create_automation` 只用于“每天晚上 8 点”或“有人进入房间时”等持久规则，不用于这次即时调温。

论文中的 `fresh` 冰箱组件和状态值是按公开 schema 构造的；三个工具名、`control_device` 参数格式以及 `set_target_temperature` 的 `temperature` 参数名有论文实例直接支撑。
## 4 SimuHome

### 4.1 论文明确把 Refrigerator 与 Freezer 列为两个设备类型

SimuHome 的 17 类设备中同时包含：

```text
Refrigerator
  Basic Information
  Descriptor
  RTCC Mode
  Temperature Control
  Temperature Measurement

Freezer
  Basic Information
  Descriptor
  RTCC Mode
  Temperature Control
  Temperature Measurement
```

当前代码也采用这个分法：

```text
src/simulator/domain/devices/refrigerator.py
src/simulator/domain/devices/freezer.py
```

示例家庭中有两个独立 device ID：

```json
{
  "device_id": "kitchen_fridge",
  "device_type": "refrigerator",
  "attributes": {
    "1.TemperatureControl.TemperatureSetpoint": 500
  }
}
```

```json
{
  "device_id": "kitchen_freezer",
  "device_type": "freezer",
  "attributes": {
    "1.TemperatureControl.TemperatureSetpoint": -1800
  }
}
```

### 4.2 每个逻辑设备内部仍分成测量与控制

冷藏逻辑设备的内部结构：

```text
Device kitchen_fridge
└─ Endpoint 1
   ├─ Temperature Measurement
   │  └─ MeasuredValue
   │     readonly
   │
   └─ Temperature Control
      ├─ TemperatureSetpoint
      ├─ MinTemperature
      ├─ MaxTemperature
      └─ Command SetTemperature
```

冷冻逻辑设备的结构完全相同，只是范围不同：

```text
Device kitchen_freezer
└─ Endpoint 1
   ├─ Temperature Measurement
   │  └─ MeasuredValue
   │
   └─ Temperature Control
      ├─ TemperatureSetpoint
      ├─ MinTemperature
      ├─ MaxTemperature
      └─ Command SetTemperature
```

四个值分别落在：

```text
kitchen_fridge
  TemperatureMeasurement.MeasuredValue
  TemperatureControl.TemperatureSetpoint

kitchen_freezer
  TemperatureMeasurement.MeasuredValue
  TemperatureControl.TemperatureSetpoint
```

控制通过：

```text
execute_command(
  device_id = kitchen_fridge 或 kitchen_freezer,
  endpoint_id = 1,
  cluster_id = TemperatureControl,
  command_id = SetTemperature,
  arguments = { target_temperature }
)
```

### 4.3 只读和可写不是直接写 Attribute

`TemperatureMeasurement.MeasuredValue` 被列在 `readonly_attributes` 中。

`TemperatureControl.TemperatureSetpoint` 也被列在 `readonly_attributes` 中：

```text
agent 不能直接 write_attribute(TemperatureSetpoint)
必须调用 SetTemperature Command
Command 内部更新 TemperatureSetpoint
```

这形成两层访问限制：

```text
MeasuredValue
  只读
  由模拟器的温度演化循环更新

TemperatureSetpoint
  agent 不能直接赋值
  只能通过 SetTemperature 修改
```

这是 SimuHome 与很多简化 schema 的重要差异：目标温度本身是一个状态字段，但外部写入口仍然是一个 Command。

### 4.4 与 Matter 组合设备的关系

Matter 的 Refrigerator Device Type 可以通过 Temperature Controlled Cabinet 等组合结构容纳多个温区。

当前 SimuHome 实现选择了另一条工程路径：

```text
Matter 可表达的组合冰箱
  ↓ 简化实现
SimuHome Refrigerator Device
SimuHome Freezer Device
```

因此它的结构实际是：

```text
一个物理冰箱印象
  → 两个 SimuHome 逻辑设备
     → 每个逻辑设备一组 Measurement / Control Cluster
```

这体现的是仿真器内部的设备边界，不能直接等同于所有真实 Matter 冰箱的 endpoint 结构。

### 4.5 它的组织特点

```text
物理分区
  被提升为逻辑 Device 边界

当前温度
  Temperature Measurement Cluster

目标温度
  Temperature Control Cluster

控制
  SetTemperature Command

参数约束
  MinTemperature / MaxTemperature / Step
```

优点是：

```text
每个温区的控制和状态查询独立
Matter Cluster 语义完整
命令参数可直接校验
时间推进和温度变化可独立模拟
```

代价是：

```text
上层看到两个 device_id
要恢复“它们属于同一台物理冰箱”需要额外关联
冷藏和冷冻可能被当作两台设备分别检索和统计
```

### 4.6 工具参数与执行例子：Matter 命令

参数卡：

```text
execute_command
  device_id: string                 "kitchen_fridge"
  endpoint_id: integer              1
  cluster_id: string                "TemperatureControl"
  command_id: string                "SetTemperature"
  args: object                      {"target_temperature":600}
```

完整调用：

```json
{
  "name": "execute_command",
  "arguments": {
    "device_id": "kitchen_fridge",
    "endpoint_id": 1,
    "cluster_id": "TemperatureControl",
    "command_id": "SetTemperature",
    "args": {
      "target_temperature": 600
    }
  }
}
```

```text
参数编码
  600 = 6.00°C
  -1800 = -18.00°C

返回
  code = 0
  command = SetTemperature
  old_setpoint = 500
  new_setpoint = 600
  temperature_celsius = 6.0
```

这五个参数分别定位设备、端点、能力组、命令和命令参数，缺少任一字段都无法形成完整 Matter 调用。
## 5 Miloco

### 5.1 一台 MIoT 设备由多个 Service 组成

Miloco 使用的 MIoT 设备类型 `fridge` 要求：

```text
Device Type: fridge
├─ required Services
│  ├─ fridge
│  └─ fridge-chamber
└─ optional Services
   ├─ physical-controls-locked
   ├─ ice-maker
   ├─ food-management
   └─ fridger-dev-mode
```

其中：

```text
fridge
  表示整台冰箱

fridge-chamber
  表示一个可独立测温、控温的温区服务实例
```

### 5.2 当前温度和 target-temperature 都在温区服务内

`fridge-chamber` 服务类型包含：

```text
fridge-chamber
├─ temperature
├─ target-temperature
├─ on
├─ mode
├─ quick-frozen-temperature
├─ deep-cold-temperature
├─ quick-frozen
├─ deep-cold
├─ quick-cooling
├─ quick-cooling-temperature
├─ ion-clean
├─ ion-clean-progress
├─ cold-fermentation-mode
├─ cold-brew-mode
├─ left-time
└─ holiday-mode
```

因此四个值在 MIoT 语义层的位置是：

```text
温区服务实例 fresh
├─ temperature
└─ target-temperature

温区服务实例 freezer
├─ temperature
└─ target-temperature
```

这里 `temperature` 和 `target-temperature` 都是 Property。它们是否为 readable、writeable、notify，由具体设备的 MIoT-SPEC 中 `access` 决定。

### 5.3 一台冰箱可以用多个 siid 区分温区

MIoT 设备实例的 Property IID 形如：

```text
prop.{siid}.{piid}
```

示意结构：

```text
Device
└─ did = refrigerator_01
   ├─ service fridge
   │  └─ 整机状态、模式、故障等
   │
   ├─ service fridge-chamber
   │  ├─ siid = s1
   │  ├─ service description = 冷藏室
   │  ├─ prop.0.s1.piid_temperature
   │  └─ prop.0.s1.piid_target_temperature
   │
   └─ service fridge-chamber
      ├─ siid = s2
      ├─ service description = 冷冻室
      ├─ prop.0.s2.piid_temperature
      └─ prop.0.s2.piid_target_temperature
```

其中具体的 `s1`、`s2` 和 `piid` 必须来自真实设备的 SPEC，上面的编号仅用于说明层级。

温区名称来自服务实例描述。Miloco 的代码支持用 `sub_device_names`：

```text
siid → 用户自定义温区名
```

覆盖服务描述。因此同一套 `fridge-chamber` 类型可以被命名为冷藏室、冷冻室、变温室等。

### 5.4 MIoT lite spec 怎样交给模型

完整 MIoT-SPEC 包含：

```text

Service Type
Property Type
Action
Event
access
format
unit
value_range
value_list
```

Miloco 将它投影成 lite spec：

```text
prop.0.{siid}.{piid}
├─ description
├─ format
├─ readable
├─ writeable
├─ unit
├─ value_range
├─ value_list
├─ type_name
└─ service_type_name
```

对冰箱温区可以理解成：

```text

  service_type_name = fridge-chamber
  service_description = 冷藏室
  type_name = temperature

  service_type_name = fridge-chamber
  service_description = 冷藏室

```

上层模型不必知道 `temperature` 和 `target-temperature` 在原始 URN 中的完整类型地址，只需要看到：

```text

  只读数值

冷藏室目标温度
  可读、可写数值
```

### 5.5 完整 SPEC 与对外白名单是两层

Miloco 还另有一份 `whitelist.json`。当前冰箱条目包括：

```text

category = 冰箱
service_type_name = fridge
prop / mode

category = 冰箱
service_type_name = fridge-chamber
prop / on

category = 冰箱
```

需要分开看：

```text
MIoT-SPEC
  设备本体存在哪些能力

whitelist
  哪些能力允许进入 Miloco 对外工具面

specific device instance
  当前这台设备实际实现了哪些可选 Property
```

服务类型里存在 `temperature` 和 `target-temperature`，不等于每台冰箱都一定实现两者，也不等于两者一定都进入当前白名单和 token 预算。

### 5.6 它的组织特点

```text

  一台 MIoT Device
```

## 6 四个项目并排对照

| 项目 | 物理设备边界 | 冷藏当前温度 | 冷冻当前温度 | 冷藏目标温度 | 冷冻目标温度 | 控制入口 |
|---|---|---|---|---|---|---|
| PersonalHomeBench | 一台冰箱属于一个 ApplianceObject | ApplianceObject 内部状态 | ApplianceObject 内部状态 | ApplianceObject 内部状态 | ApplianceObject 内部状态 | 冰箱自身 feature；精确公开名称未给出 |
| SMH-Bench | 一台冰箱 Device | `fresh.current_temperature` | `freezer.current_temperature` | `fresh.target_temperature` | `freezer.target_temperature` | `fresh.set_target_temperature`、`freezer.set_target_temperature` |
| SimuHome | 当前实现拆成 Refrigerator 与 Freezer 两个逻辑 Device | `kitchen_fridge.TemperatureMeasurement.MeasuredValue` | `kitchen_freezer.TemperatureMeasurement.MeasuredValue` | `kitchen_fridge.TemperatureControl.TemperatureSetpoint` | `kitchen_freezer.TemperatureControl.TemperatureSetpoint` | 各自执行 `SetTemperature` Command |
| Miloco | 一台 MIoT Device | `fridge-chamber.temperature` | `fridge-chamber.temperature` | `fridge-chamber.target-temperature` | `fridge-chamber.target-temperature` | 写 `target-temperature` Property，或按设备能力走 Action |

四个项目内部还有一层共同规律：

```text
当前温度
  由冰箱自身的设备状态、硬件上报或仿真演进产生
  agent 主要读取

目标温度
  是可观察的当前状态
  也是控制后的目标状态

控制
  通过 Service / Command / feature / writable Property 执行
  成功后通过目标温度回读确认
```

### 6.1 四种工具面的参数数量

| 项目 | 固定定位参数 | 能力参数 | 返回或验证 |
|---|---|---|---|
| PersonalHomeBench | 设备名、feature 名 | `feature_kwargs` 中 `0..N` 个 | feature 返回值和设备状态 |
| SMH-Bench | `did`、`locator` | `arguments` 中 `0..N` 个 | `ok` 与状态变化 |
| SimuHome | `device_id`、`endpoint_id`、`cluster_id`、`command_id` | `args` 中 `0..N` 个 | Result、状态变化、回读 |
| Miloco | `did`、`iid` | 单个 `value`；Action 时可为数组 | RPC 返回值和状态回读 |

四个对象的共同设计由此很清楚：

```text
定位设备
  ↓
定位能力
  ↓
提供该能力自己的参数
  ↓
执行
  ↓
返回结果或状态变化
```

我们的 MCP 应该吸收这个结构，同时把四个项目各自不同的定位字段压缩成：

```text
device_id
capability_id
arguments
readback
```

## 7 四种组织路线的本质差异

### 7.1 PersonalHomeBench：家庭层拆对象，冰箱内部收在 ApplianceObject

```text
Household
├─ appliances[]
│  └─ refrigerator ApplianceObject
│     ├─ detailed state
│     └─ features
└─ sensors[]  本次不纳入
```

它优先回答：

```text
这台冰箱当前详细状态是什么
这台冰箱支持哪些 feature
怎样执行冰箱 feature
```

家庭层虽然把 `appliances[]` 和 `sensors[]` 分开，进入单个冰箱目录后，冷藏和冷冻读数仍应作为该 `ApplianceObject` 的内部状态处理。

### 7.2 SMH-Bench：按设备内功能组件拆

```text
Home
└─ devices[]
   └─ refrigerator
      ├─ fresh Component
      └─ freezer Component
```

它优先回答：

```text
每台设备有哪些状态
有哪些可执行服务
多组件设备如何避免同名能力冲突
```

### 7.3 SimuHome：按 Matter 逻辑设备与 Cluster 拆

```text
Refrigerator Device
  Temperature Measurement
  Temperature Control

Freezer Device
  Temperature Measurement
  Temperature Control
```

它优先回答：

```text
某个 device_id 下有哪些 endpoint / cluster
某个 cluster 有哪些 attribute / command
命令参数是否满足协议约束
```

### 7.4 Miloco：按 MIoT 设备、服务和属性拆

```text
Fridge Device
  fridge Service
  fridge-chamber Service × N
    temperature Property
    target-temperature Property
```

它优先回答：

```text
这台真实设备的 SPEC 是什么
每个温区服务实例的 siid 是什么
每个属性是否 readable / writeable
哪些能力进入模型可见目录
```

## 8 对我们自己的设备能力模型意味着什么

一台物理冰箱应当保留一个稳定设备身份：

```text
Device
├─ identity
│  └─ refrigerator_01
├─ summary
│  └─ 双温区冰箱，可读取和设置冷藏、冷冻温度
├─ zones
│  ├─ fresh
│  │  ├─ observe
│  │  │  └─ current_temperature
│  │  └─ control
│  │     ├─ set_target_temperature
│  │     └─ readback_target_temperature
│  └─ freezer
│     ├─ observe
│     │  └─ current_temperature
│     └─ control
│        ├─ set_target_temperature
│        └─ readback_target_temperature
└─ optional
   ├─ door_state
   ├─ mode
   ├─ quick_cool
   └─ quick_freeze
```

这里需要遵守三个组织原则：

```text
第一，物理身份与功能分区分开
  一台冰箱仍是一个 Device
  fresh / freezer 是 Device 内 zone

第二，当前值与目标值分开
  current_temperature 是纯观测
  target_temperature 是控制后的目标状态和读回值

第三，状态与动作分开
  target_temperature 负责保存值
  set_target_temperature 负责修改它
```

目标温度不建议在两个不同位置各复制一份：

```text
observe.target_temperature = 5
control.target_temperature = 5
```

更稳妥的方式是只保存一个目标状态，让控制项引用它的读回位置：

```text
control
  id: refrigerator.fresh.set_target_temperature
  current_value_source: refrigerator.fresh.target_temperature
  verify:
    readback: refrigerator.fresh.target_temperature
```

这样模型能看到当前目标和控制入口，运行时也只有一个事实来源。
