# 12：设备能力三分与组件约束

核验日期：2026-10-29

本文讨论三个问题：

```text
设备与房间怎样关联
一个设备内部的能力怎样拆
必选、可选、常见、不常见之间怎样避免概念重复
```

## 0 结论

你的三分法可以成立，但需要明确：

```text
设备
├─ Topology
│   └─ 位于哪个房间、服务哪些区域
├─ Capability Card
│   ├─ Summary
│   │   └─ 设备能力文字摘要
│   ├─ Observe
│   │   └─ 只读能力
│   └─ Control
│       └─ 可写属性和可执行动作
```

其中：

```text
Observe
  当前温度、门状态、在线状态、故障状态、当前模式

Control
  设定温度、切换模式、开关、风速、摆风、定时

Summary
  用一段稳定的文字说明设备是什么、能做什么
```

这三块是“信息类型”，不是三档可见性。

可见性建议仍只保留两档：

```text
common
  高频、低参数复杂度、适合默认展示和合成数据

custom
  低频、品牌特有、参数复杂或仅特定任务需要
```

另外单独保留一个 Profile 准入门槛：

```text
required
  设备必须具备这些条件，才能声称自己属于该 Profile
```

`required` 描述“是否算这类设备”，`common/custom` 描述“默认是否展示、是否用于合成数据”。这样不必再建立第三档能力可见性。

## 1 房间与设备

拓扑关系保持简单：

```text
Room
  └─ contains → Device
```

每条关系至少保存：

```yaml
room_id: living_room
device_id: ac_living_room
relation_type: placed_in
```

中央空调、全屋新风、地暖等设备还可能影响多个房间：

```text
placed_in
  设备自身安装在哪里

serves
  设备能够影响哪些区域
```

做第一版时可以只实现 `placed_in`。如果设备本身支持多区域控制，再增加 `serves_area_ids` 或 `zone_ids`，不需要把空间关系塞进设备能力。

## 2 为什么叫 Observe，而不叫 Sensor

只读信息不一定是 HA 的 `sensor` domain：

```text
当前温度        sensor
门开状态        binary_sensor
当前模式        select 或 attribute
电源状态        switch 的 state，但当前端侧只读
故障码          sensor
门开事件        event
```

因此第一部分建议叫：

```text
observe
  只能读取的当前状态和上下文
```

`sensor` 可以继续作为具体能力类型，但不适合作整个大类的名称。

## 3 能力卡的数据结构

一个设备的端侧视图可以由以下结构组成：

```yaml
device_view:
  device_id: refrigerator_01
  profile: refrigerator
  room_id: kitchen

  summary: "双温区冰箱，可查看冷藏和冷冻温度、设置目标温度并检测门状态。"

  observe:
    common:
      - id: refrigerator.cold.current_temperature
        value: 4
        unit: celsius
      - id: refrigerator.freezer.current_temperature
        value: -20
        unit: celsius
      - id: refrigerator.door_state
        value: closed
    custom:
      - id: refrigerator.filter_remaining
      - id: refrigerator.power_consumption

  control:
    common:
      - id: refrigerator.set_target_temperature
        zone: cold
        current_value: 5
        range: [2, 8]
        step: 1
      - id: refrigerator.set_target_temperature
        zone: freezer
        current_value: -17
        range: [-24, -15]
        step: 1
    custom:
      - id: refrigerator.set_quick_cool
      - id: refrigerator.set_quick_freeze
      - id: refrigerator.set_holiday_mode
```

结构原则：

```text
只读能力放 observe
可写属性和动作放 control
同一属性的当前值放 control item 自身
文字摘要由 profile 和实际能力生成
```

存储主键不能只用 `capability_id`。冰箱两个温区都可能有 `set_target_temperature`，唯一键应为：

```text
profile + section + capability_id + scope/zone
```

例如温度设定：

```text
observe
  current_temperature

control
  set_target_temperature
  current_value = 5
```

这样不会在 `observe` 和 `control` 中各放一个 `target_temperature`。

## 4 必选、可选、常见、不常见

这里建议避免把四个词做成四个互斥枚举。它们实际上属于两个不同问题。

### 4.1 必选与可选属于 Profile 契约

必选不是一种 Entity，也不是一种可见性。它是 Profile 的准入门槛：

```text
required_all
  必须同时存在的能力

required_any
  至少存在一个的能力

optional
  允许出现，但缺失不影响 Profile 成立
```

例如：

```yaml
profile: air_conditioner
admission:
  required_all:
    - control.set_power
    - control.set_target_temperature

optional:
  - control.set_hvac_mode
  - control.set_fan_speed
  - control.set_swing_vertical
  - control.set_swing_horizontal
  - control.set_timer
```

如果某设备没有 `set_target_temperature`：

```text
不能声称它是标准 air_conditioner
可以降级为 generic_climate
也可以只作为只读空调状态设备
```

是否允许“所有能力都可选”，技术上可以。代价是 Profile 变得很弱，任何带一个开关的设备都可能声称是空调。因此建议每个设备 Profile 至少保留一个非常小的准入门槛。

### 4.2 常见与不常见属于任务采样策略

`common/custom` 回答的是：

```text
默认给端侧模型看什么
合成任务优先使用什么
什么时候需要按需展开
```

例如：

```text
空调 common
  power
  target_temperature
  hvac_mode
  fan_speed

空调 custom
  swing_vertical
  swing_horizontal
  sleep_mode
  eco_mode
  boost_mode
  self_clean
  timer
  display
```

常见项不等于所有设备都有。它是“有则默认使用”的高频能力集合。

### 4.3 最终只保留两档能力可见性

```text
common
custom
```

`required` 仅在 Profile 准入时读取，不作为第三档能力列表。

建议约束：

```text
required_for_profile ⊆ common
```

这样可以保证合成器看到的公共能力至少覆盖 Profile 成立所需的核心能力。

## 5 空调的能力卡

### 5.1 推荐准入条件

不建议使用“开关 + 风速”作为空调准入：

```text
风扇和空气净化器也可能有开关 + 风速
无法区分设备类型
```

更稳的准入条件：

```yaml
profile: air_conditioner
identity_evidence:
  any_of:
    - matter:RoomAirConditioner
    - miot:air-conditioner
    - midea:0xAC
    - tuya:kt
    - lg:AIR_CONDITIONER

admission:
  required_all:
    - control.set_power
    - control.set_target_temperature
```

这样定义的是“可调温空调”。

如果目标设备只有开关、模式和风速，没有温度控制：

```text
更适合归入 generic_climate 或 fan
不建议放宽 air_conditioner 的准入到无法区分设备类型
```

### 5.2 能力分层

```yaml
profile: air_conditioner

summary: "可开关、调节运行模式和目标温度；支持风速和摆风时可按需展开。"

observe:
  common:
    - online
    - current_temperature
    - fault_state
  custom:
    - humidity
    - outdoor_temperature
    - energy_consumption
    - filter_remaining

control:
  common:
    - set_power
    - set_target_temperature
    - set_hvac_mode
    - set_fan_speed
  custom:
    - set_swing_vertical
    - set_swing_horizontal
    - set_timer
    - set_sleep_mode
    - set_eco_mode
    - set_boost_mode
    - set_self_clean
    - set_fresh_air
    - set_display

hidden:
  - factory_reset
  - pairing
  - firmware_update
  - raw_protocol_write
```

`set_hvac_mode` 和 `set_fan_speed` 是 common，同时仍是 optional。设备没有该能力就不输出，不报错。

### 5.3 为什么选择这个最小核心

```text
开关 + 风速
  能控制，但无法识别空调

开关 + 模式 + 设定温度
  语义完整，但排除了没有模式选择或只做自动模式的设备

开关 + 设定温度
  更小的可调温核心
  设备族证据另外负责排除恒温器、热水器等近似设备
```

当前建议采用：

```text
设备族证据
  +
set_power
  +
set_target_temperature
  =
air_conditioner 准入
```

模式、风速、摆风作为能力组件出现，不用它们决定设备是不是空调。

## 6 冰箱的能力卡

```yaml
profile: refrigerator

summary: "冰箱，可查看各温区当前温度和门状态，并对支持的温区设置目标温度。"

observe:
  common:
    - cold.current_temperature
    - freezer.current_temperature
    - cold.door_state
    - freezer.door_state
    - online
    - fault_state
  custom:
    - filter_remaining
    - defrost_state
    - compressor_speed
    - power_consumption

control:
  common:
    - cold.set_target_temperature
    - freezer.set_target_temperature
  custom:
    - set_mode
    - quick_cool
    - quick_freeze
    - holiday_mode
    - ice_maker
    - sabbath_mode
    - door_assistant

hidden:
  - calibration
  - factory_reset
  - network_config
  - raw_property_write
```

冰箱准入可以设得比空调更宽：

```yaml
admission:
  required_all:
    - refrigerator identity
  required_any:
    - cold.current_temperature
    - freezer.current_temperature
    - cold.set_target_temperature
    - freezer.set_target_temperature
```

这样能兼容：

```text
只能看温度的冰箱
可以调温的冰箱
只有温度等级 select、没有精确 setpoint 的冰箱
```

合成数据按实际存在的 common 能力生成，不会假设每台冰箱都能精确设置温度。

## 7 文字摘要怎样生成

文字摘要属于派生信息，不能作为第一事实来源。

```text
Profile 定义
  +
设备实例实际能力
  ↓
确定性模板或受约束生成
  ↓
capability_summary
```

建议摘要只包含：

```text
设备类别
温区或主要组件
常用只读能力
常用控制能力
明确的可选能力提示
```

例如空调：

```text
"这是空调，可开关、调节目标温度和运行模式，并查看当前温度；
该设备支持风速和上下摆风，支持睡眠与节能模式。"
```

例如冰箱：

```text
"这是双温区冰箱，可查看冷藏和冷冻当前温度、门状态，
并可分别设置两个温区的目标温度；支持速冷与速冻。"
```

摘要约束：

```text
不得出现当前设备不存在的能力
不得写 Entity ID、协议字段或品牌内部参数
默认只描述 common
custom 只用一句概括
hidden 永不出现
长度控制在一到三句
```

如果摘要由 LLM 生成，必须用能力 ID 白名单校验，防止写出不存在的“支持自动清洁”或“支持远程开门”。

## 8 MCP 默认返回什么

第一轮 `inspect_device` 建议返回：

```text
summary
common observe 的当前值
common control 的能力摘要
```

例如空调：

```json
{
  "device_id": "ac_living_room",
  "profile": "air_conditioner",
  "summary": "空调，可开关、调温和调节模式，当前支持风速。",
  "observe": {
    "current_temperature": 26.0,
    "online": true
  },
  "control": {
    "set_power": "boolean",
    "set_target_temperature": {
      "current": 24,
      "min": 17,
      "max": 30,
      "step": 0.5
    },
    "set_hvac_mode": [
      "auto",
      "cool",
      "heat",
      "dry",
      "fan_only"
    ],
    "set_fan_speed": [
      "auto",
      "low",
      "medium",
      "high"
    ]
  }
}
```

扩展能力通过另一个查询展开：

```text
inspect_capabilities(device_id, tier="custom")
```

执行仍使用稳定能力 ID：

```text
execute_capability(
  device_id,
  capability_id="set_target_temperature",
  arguments={"value": 25}
)
```

这样不需要为每种设备的每个旋钮创建一个 Tool。

## 9 合成数据策略

合成器只使用：

```text
Profile required
  +
common observe
  +
common control
```

`custom` 用于：

```text
定向评测
复杂任务
品牌特有能力测试
人工审查
```

建议生成顺序：

```text
1 从 common observe 中生成环境或状态查询任务
2 从 common control 中生成单步调整任务
3 组合同一 Profile 的多个 common control
4 只在已有 common 能力不足时引入 custom
5 永远不生成 hidden 能力任务
```

例如空调：

```text
常见任务
  打开空调
  调至 25°C
  切换到制冷
  风速调高
  当前温度是多少

不常见任务
  打开自清洁
  设置上下摆风
  调整屏显
```

这能让训练分布稳定，同时保留长尾能力接入空间。

## 10 最终建议

```text
房间与设备
  用一条或两条拓扑关系表达

设备内部
  使用 Observe / Control / Summary 三分

能力可见性
  只使用 common / custom 两档

Profile 合法性
  使用独立的 required_all / required_any 门槛

合成数据
  优先 required 与 common

长篇能力说明
  不放进每个能力字段
  统一生成一个短 Summary
```

这套结构体现的正是你的两个判断：不同设备可以接入不同组件；训练数据只需要围绕必选与高频常见组件生成，不必让端侧模型承担整个插件的全部能力面。
