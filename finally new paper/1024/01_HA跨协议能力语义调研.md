# 01：HA 跨协议能力语义调研

日期：2026-10-24

目标：判断能否利用 Home Assistant Core、厂商插件和社区插件的开源代码，汇总不同协议设备实际暴露给 HA 的能力，再压缩成 Agent 可使用的统一语义。

## 1 结论

能做，但要把“能力事实”和“Agent 视图”分成两层。

```text
能力事实层
  尽量完整，保留设备、实体、动作、参数、范围、事件、来源和不确定性

Agent 视图层
  强压缩，只暴露少量稳定动作和当前设备真正可用的能力
```

Home Assistant 已经是跨协议操作面的共同落点。Matter、ZHA、Z-Wave JS、MQTT、米家、美的、Tuya 等最终都会投影成 HA 的设备、实体、属性和服务。因此，运行时注册表和插件源码可以作为跨协议能力发现的主事实源。

这套方法能回答“通过 HA 现在实际能做什么”。设备物理上“理论上还能做什么”，插件代码可能知道，也可能没有接出来，仍需协议文档或真机探测补足。

## 3 HA 已有的共同语义

HA Core 的实体与服务模型已经提供了一批可机读字段：

```text
实体身份
  entity_id、unique_id、platform、config_entry_id

设备与空间
  device_id、device registry、area registry

能力提示
  supported_features、capability_attributes、entity_category

状态语义
  device_class、state_class、unit_of_measurement

名称与枚举
  translation_key、entity translations、service translations

动作接口
  domain.service、service schema、target selector

当前能力
  state、attributes、min、max、step、options、event_types
```

这些字段可以作为第一版 Capability IR 的共同骨架。

### 3.1 米家冰箱的运行时实例

当前实例已经能直接提取出以下能力：

```text
number 冷藏设定温度
  min=2, max=8, step=1, unit=°C

number 冷冻设定温度
  min=-24, max=-15, step=1, unit=°C

select 冰箱模式
  options=[手动, 智能, 假日, 速冷, 速冻]

sensor 冷藏/冷冻温度
  device_class=temperature
  state_class=measurement

sensor 故障码
  原始状态和位图解释

sensor 门未关提醒
  device_class=enum
  options=[无, 有门未关]

event 门开提醒
  event_types=[门开提醒]

button 恢复出厂设置
  有暴露，但应被策略层限制
```

这组实例说明两件事：

```text
一  HA 插件确实暴露了比通用动作词表更丰富的真实能力
二  能力本体不能按“允许 Agent 做什么”来删减
    恢复出厂设置应保留为高风险能力，不能从语义模型中消失
```

## 4 代表性协议与插件

### 4.1 Matter

本地 Core 的 `matter` 集成把 Matter 端点、集群和属性转换成 HA 平台实体。实现中大量使用 `entity_description`、`translation_key`、`supported_features` 与属性转换。

```text
Matter endpoint / cluster / attribute / command
                    ↓
HA platform entity description
                    ↓
light / climate / number / sensor / event / button ...
```

Matter 的优势是上游有正式集群模型，适合提供强类型、可回溯的静态语义；HA 侧则决定最终向 Agent 暴露哪些实体。

### 4.2 ZHA 与 Z-Wave JS

ZHA 和 Z-Wave JS 都使用 HA 标准平台，但能力来自各自协议簇或命令类：

```text
ZHA          Zigbee cluster → ZHA entity features → HA entity
Z-Wave JS    Command Class / Value → HA entity → HA service
```

两者都通过 `supported_features` 和额外属性表达差异。仅看实体类型，不知道灯具是否支持色温、风扇是否有摆头、空调是否支持目标温度区间。

### 4.3 MQTT

MQTT 本身只承载消息。设备语义主要由 discovery 配置决定，例如：

```text
supported_features
device_class
state_class
payload_on / payload_off
value_template
command_topic / state_topic
```

因此 MQTT 的“真相”位于运行时 discovery 配置和 retained 消息，不在协议本身。

### 4.4 米家官方插件

`xiaomi_home` 直接读取 MIoT 设备规格，再按 HA 平台生成实体。它已覆盖：

```text
light、climate、cover、fan、humidifier、media_player、
switch、sensor、binary_sensor、number、select、
event、button、text、vacuum、water_heater
```

MIoT 的 `service/property/action` 与 HA 的实体动作之间存在多层映射。运行时可看到结果，底层约束与枚举仍要回读 MIoT spec 或插件代码。

### 4.5 美的插件

外部 HACS 插件 `georgezhao2010/midea_ac_lan` 当前浅克隆版本为 `v0.3.22`，声明 `iot_class=local_push`，覆盖空调、冰箱、洗衣机、热水器、微波炉、风扇、空气净化器等大量家电。

它同时包含：

```text
标准 HA 平台实体
  climate / fan / humidifier / light / lock / number /
  select / sensor / switch / water_heater

厂商低层能力
  set_attribute(attribute, value)
  send_command(cmd_type, cmd_body)
  midea_devices.py 中的设备能力表
```

低层命令很有价值，但不能直接塞给 Agent。它们应进入原始能力层，并在压缩视图中映射成有类型、有范围、有风险标签的能力。

### 4.6 Tuya

Tuya 同时存在多条接入路线：

```text
HA Core tuya       官方云集成，按产品类别映射成 HA 平台实体
smartlife           新官方云端插件，当前仍为 beta，按 DPCode/DPType 组织能力
localtuya           本地 DP 接入，用户把具体 DP 配置成 switch/light/climate 等实体
```

LocalTuya 暴露了一个关键差异：同一产品最终生成什么能力，部分取决于用户配置。因此只看插件静态代码不够，必须读取实际 config entry 和实体注册表。

## 5 可抽取性判断

| 抽取内容 | 可行性 | 依据 | 主要风险 |
| --- | --- | --- | --- |
| 枚举集成、设备和实体 | 高 | manifest、config entry、device/entity registry | 仅安装实例可见，不能代表全部设备 |
| 抽取标准动作与当前状态 | 高 | HA services、states、attributes | 动作名称统一，参数语义仍可能不同 |
| 抽取范围、枚举、单位 | 中高 | number/climate/select/sensor 属性，插件代码 | 并非所有集成都完整暴露 |
| 抽取事件、按钮和故障能力 | 中高 | event/button/sensor 实体 | 容易被统一动作词表误删 |
| 追溯协议原始语义 | 中 | Matter/MIoT/ZCL/DP/CC 源码 | 每个协议需要专门适配 |
| 推断副作用与因果关系 | 低 | 静态代码通常没有统一表达 | 需环境仿真、真机探测或人工规则 |
| 自动覆盖全部第三方插件 | 中低 | 插件质量与结构差异大 | 依赖、动态数据、私有实现、版本漂移 |

综合判断：

```text
统一枚举和运行时能力发现
  可以做到几乎全量覆盖

统一静态语义深度解析
  只能覆盖遵守 HA 公共模式的插件
  长尾插件需要专门适配或人工校验

物理因果与真实副作用
  不能仅靠插件代码保证
```

## 6 压缩策略

压缩是必须的，但压缩应作用于“视图”，不能删除底层事实。

```text
完整能力图
  保留全部实体、动作、参数、事件、范围、来源和风险

能力原子
  binary_switch
  numeric_setpoint
  level
  position
  enum_mode
  event
  command
  compound_capability

能力档案 profile
  把多个原子组合成常见设备视图
  例如 thermostat、dimmable_light、position_cover、washer

Agent 视图
  当前设备当前可执行的最小动作集
  需要时展开参数、范围和风险
```

Agent 不需要一次看到 1,483 个集成的所有能力。它只需要四类稳定操作：

```text
observe    读取当前状态与可观察量
act        调用某个 capability_id，并传入带类型参数
subscribe  订阅事件、告警和设备状态变化
configure  配置或调整设备行为
```

以温度为例：

```text
米家 number 冷藏设定
美的 climate 目标温度
LocalTuya climate 的 TEMP_SET DP
Matter Thermostat 的 OccupiedCoolingSetpoint

                   ↓ 压缩

temperature_setpoint
  value、unit、min、max、step、source
```

压缩后保留来源链：

```text
capability_id
  → HA entity_id
  → config_entry / integration
  → 插件中的 handler
  → 原始协议字段
```

这样 Agent 看到短接口，排查时仍可回到真实来源。

## 7 Capability IR 草案

```json
{
  "capability_id": "xiaomi.fridge.cold.target_temperature",
  "kind": "numeric_setpoint",
  "source": {
    "protocol": "miot",
    "integration": "xiaomi_home",
    "entity_id": "number.midjd6_cn_911432173_6101_target_temperature_p_3_2",
    "raw_ref": "siid=3, piid=2"
  },
  "parameter": {
    "name": "target_temperature",
    "type": "number",
    "unit": "°C",
    "min": 2,
    "max": 8,
    "step": 1
  },
  "constraints": {
    "available": true,
    "preconditions": [],
    "mapping": "exact"
  },
  "effects": {
    "immediate": "target_temperature",
    "verify": "read_back",
    "side_effects": "unknown"
  },
  "risk": "normal",
  "evidence": ["ha_runtime", "integration_code", "verified"]
}
```

字段解释：

```text
kind          固定能力原子，方便压缩和通用操作
source        保留协议、集成、实体和原始字段
parameter     参数类型、单位、范围、步长、枚举
constraints   当前是否可用、前置条件、映射是否有损
effects       动作结果、验证方式、已知副作用
risk          行为策略，不属于设备本体
evidence      该项语义来自运行时、代码、协议还是实测
```

## 8 抽取流水线

```text
1 集成清单
  扫描 manifest、HACS 元数据和 HA config entries

2 实例关联
  通过 device registry、entity registry、area registry
  把 integration → device → entity 关联起来

3 运行时能力
  读取 states、attributes、supported_features、
  min/max/step/options/event_types

4 服务语义
  读取 HA services、字段定义、target selector、
  translation 和 entities 支持的 action

5 静态补充
  扫描插件的 entity description、spec 表、DP/cluster 映射、
  service handler 和原始协议字段

6 经验验证
  对读写能力做低风险探测
  记录 verified、延迟、错误码和回读结果

7 压缩编译
  映射成能力原子和 profile
  生成 Agent 所需的当前上下文动作集
```

## 9 必须保留的边界

```text
插件暴露 ≠ 物理设备全集
  HA 能控制的是插件实际暴露的部分

静态代码 ≠ 当前实例
  同一产品型号可能因配置、固件、账号和实体过滤而不同

统一动作 ≠ 统一副作用
  相同 turn_on 在不同设备上可能有不同启动过程与延迟

实体可用 ≠ 操作合法
  参数范围、前置条件、并发冲突和云端时延仍需验证

压缩视图 ≠ 原始能力
  压缩后的动作必须保留到原始实体和协议字段的引用
```

## 10 建议的最小实现

第一版不做 1,483 个集成的深度解析器。先做能产生研究价值的最小闭环：

```text
P0  全量运行时索引
    HA 里有什么 integration/device/entity/service
    当前实体有哪些能力属性

P1  五个高价值适配器
    matter、zha / zwave_js、mqtt、
    xiaomi_home、midea_ac_lan

P2  能力压缩
    capability atoms + device profiles
    生成按设备裁剪的 Agent action schema

P3  安全探测
    只读探测优先
    写操作需要显式确认
    记录 verified 和副作用

P4  覆盖扩展
    先用通用 AST / manifest / runtime 规则覆盖长尾
    再按使用频率补专门适配器
```

第一版应当证明的不是“已经理解所有协议”，而是以下三件事：

```text
同一能力可以从不同协议汇总到同一 capability_id
同一设备不会因为在不同插件下而生成完全不同的 Agent 动作
压缩后的 Agent 视图可以回溯到真实 HA 实体和协议字段
```

## 12 本次结论的边界

已验证：

```text
本地 HA Core 具备统一能力字段和集成规模
Matter/ZHA/Z-Wave/MQTT/Tuya 等确实投影到相同 HA 平台
米家运行时能直接看到范围、枚举、事件、按钮和故障指标
美的、Tuya、LocalTuya 外部插件均采用 HA 实体模型
不同插件的底层语义密度和暴露方式差异很大
```

推断：

```text
可以构建跨协议 capability index
核心价值来自运行时索引和协议来源链
深度覆盖需要少量高价值专用适配器
```

仍待验证：

```text
同一能力跨协议映射的一致率
压缩后 Agent 动作 schema 的可用性
静态代码解析对长尾插件的覆盖率
副作用和时延能否通过探测稳定获得
```
