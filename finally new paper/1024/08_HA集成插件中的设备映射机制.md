# 08：HA 集成插件中的设备映射机制

调研日期：2026-10-27

## 结论

插件源码里的内容可以分成四层：

```text
协议适配代码
  怎么连接、鉴权、收发消息

通用转换规则
  协议字段如何变成 HA entity

型号/设备类型特例
  某些型号需要改名、裁剪、单位转换、特殊状态映射

运行时的真实设备
  用户账号或本地网络发现到的设备实例、型号、URN、状态和属性
```

多数插件并不会在源码中预置“世界上所有型号及其全部能力”。真实设备列表通常要等用户登录或设备被发现后才出现。

插件源码能提供的是：

```text
设备能力如何被解释
能力如何映射为 HA entity
哪些型号需要特殊修补
某协议支持哪些设备类型
```

真正完整的单台设备能力，还需要在运行时组合：

```text
设备实例
  + 型号
  + 厂商/协议能力描述
  + 实体注册表
  + 当前状态与属性
  + 插件转换规则
```

## 1 Xiaomi Home：动态 MIoT SPEC 为主

源码位置：

```text
ha_integration_sources/13_xiaomi_home_custom/
```

### 1.1 运行时先拿到设备与 MIoT SPEC

设备导入流程：

```text
小米账号 OAuth 登录
  ↓
从小米云端获取家庭和真实设备列表
  ↓
每台设备带有 model、did、urn 等元数据
  ↓
根据 urn 获取 MIoT-Spec-V2
  ↓
缓存 SPEC
  ↓
按转换规则创建 HA entity
```

所以插件源码自身不是设备清单。你家里有哪些冰箱、空调、灯，取决于登录后云端返回的实际设备。

### 1.2 默认的通用属性转换

`specv2entity.py` 读 MIoT SPEC 后，按属性能力创建 HA entity：

| MIoT 属性 | HA entity |
|---|---|
| 可写 `string` | `text` |
| 可写 `bool` | `switch` |
| 可写非字符串/布尔，带 `value-list` | `select` |
| 可写非字符串/布尔，带 `value-range` | `number` |
| 只读属性 | `sensor` |
| 事件 | `event` |
| 无参数动作 | `button` |
| 有参数动作 | `notify` |

例如一个 MIoT 冰箱 SPEC 中：

```text
temperature
  access: read
  format: float
  → sensor

target-temperature
  access: read/write
  format: int
  value-range: [2, 8, 1]
  → number

mode
  access: read/write
  value-list: ...
  → select
```

这是由 SPEC 形态推导出的结果，不需要源码里出现“某型号冰箱”的完整枚举。

### 1.3 设备级与 service 级专用映射

`specv2entity.py` 还包含：

```text
SPEC_DEVICE_TRANS_MAP
  设备整体的 service/property/action 组合满足条件时，
  映射为 climate、vacuum、humidifier、media_player 等专门 entity

SPEC_SERVICE_TRANS_MAP
  某个 service 满足条件时，映射成专门 HA entity

SPEC_PROP_TRANS_MAP
  属性名称对应 device_class、单位、状态类等

SPEC_EVENT_TRANS_MAP
  特定事件映射
```

这里依然主要是“能力形态规则”，不是按每个真实设备 DID 建表。

### 1.4 型号特例规则

Xiaomi 插件确实带了型号级修补，主要在：

```text
integration/miot/specs/spec_filter.yaml
  某型号要忽略哪些 service/property/event/action

integration/miot/specs/spec_modify.yaml
  某型号要改名、改格式、改单位、改 value-list、加表达式转换

integration/miot/specs/spec_add.json
  补充云端 SPEC 缺失的内容

integration/miot/specs/bool_trans.yaml
  bool 值与 HA 状态的转换

integration/miot/specs/multi_lang.json
  名称和说明翻译
```

实际例子：

```yaml
urn:miot-spec-v2:device:air-conditioner:0000A004:daikin-k5:1:
  prop.2.2:
    format: string
    expr: '{"COOL":0,"DEHUMI":1,"DRY":1,"FAN":2,"HEAT":4}.get(src_value,src_value)'

urn:miot-spec-v2:device:air-purifier:0000A007:zhimi-ua1a:3:
  prop.3.5:
    expr: (src_value*6)
```

这类规则说明：

```text
云端 SPEC 并不总是足够
少数型号还需要本地补丁
补丁以 URN / 型号为键，而不是以用户设备名称为键
```

`const.py` 另有少量明确不支持型号：

```text
chuangmi.ir.v2
era.airp.cwb03
hmpace.motion.v6nfc
k0918.toothbrush.t700
```

### 1.5 米家冰箱在插件源码里有没有直接映射

在当前 Xiaomi Home 插件源码中搜索：

```text
fridge
refrigerator
freezer
冰箱
冷藏室
冷冻室
midjd
```

结果：

```text
转换规则中没有硬编码的米家冰箱型号清单
没有找到当前米家中对开门冰箱的 midjd 型号映射
唯一明显的 fridge 条目在 LAN profile_models.yaml
```

`profile_models.yaml` 中列了 22 个 `viomi.fridge.*` 型号：

```text
viomi.fridge.m1
viomi.fridge.p1
viomi.fridge.u1
...
viomi.fridge.x7
```

这些条目只有 `ts` 时间戳。`miot_lan.py` 在发现设备时会跳过 `model in self._profile_models` 的型号，并记录 `model not support local ctrl`。因此这 22 个条目表示当前不走局域网直连的冰箱型号，不是实体结构定义，也不是“已支持本地控制”的白名单；这些设备仍可走小米云端。

因此当前米家对开门冰箱进入 HA 的路径是：

```text
云端返回真实设备
  ↓
返回 model 和 MIoT SPEC urn
  ↓
插件下载并解析该设备 SPEC
  ↓
通用属性规则把只读温度属性建成 sensor
  ↓
如果 SPEC 中有可写且有范围的目标温度属性，则建为 number
  ↓
如果整个设备匹配某类专用组合，则建成 climate/select 等实体
```

这解释了当前环境中的实际现象：

```text
冷藏室 温度   只读属性 → sensor
冷冻室 温度   只读属性 → sensor
冷藏目标温度  可写数值属性 → number（如果 SPEC 和实体都暴露）
```

HA 的 Assist 当前只暴露了前两个 `sensor`，所以官方 MCP 看不到可写目标温度入口。问题位于实体暴露和 Assist 工具面，不在 Xiaomi 插件缺少一个“冰箱型号表”。

当前 HA 实体注册表可以直接证明这一点：

```text
number.midjd6_cn_911432173_6101_target_temperature_p_3_2
  state = 5
  → 冷藏室设定温度

number.midjd6_cn_911432173_6101_target_temperature_p_4_2
  state = -17
  → 冷冻室设定温度

select.midjd6_cn_911432173_6101_mode_p_2_2
  state = 手动
  → 冰箱模式

sensor.midjd6_cn_911432173_6101_temperature_p_3_1
  state = 4
  → 冷藏室当前温度

sensor.midjd6_cn_911432173_6101_temperature_p_4_1
  state = -20
  → 冷冻室当前温度

event.midjd6_cn_911432173_6101_fault_open_e_8_1
  → 门开提醒事件

button.midjd6_cn_911432173_6101_reset_a_7_1
  → 恢复出厂设置
```

模型名 `midjd6...` 没有出现在插件静态映射文件中，但这些实体真实存在。这说明转换确实发生在运行时 MIoT SPEC 上。

### 1.6 从插件源码能得到什么

```text
能得到
  MIoT 属性如何变成 HA entity
  设备级/服务级专用匹配条件
  型号修补规则
  不支持型号清单
  当前排除局域网直连的型号清单

不能单独得到
  用户家里有哪些设备
  某台设备完整的能力集合
  某型号全部属性与当前值
  未下载到本地的云端 SPEC
```

## 2 Midea AC LAN：静态设备类型与属性映射较多

源码位置：

```text
ha_integration_sources/14_midea_ac_lan_hacs/
```

美的插件采用另一类方式：

```text
设备类型码 → 专用 device/message 类 → 固定属性集合
```

例如设备类型 `0xCA` 有专用冰箱类：

```text
midea/devices/ca/device.py
midea/devices/ca/message.py
```

其中直接定义了冰箱属性：

```text
refrigerator_actual_temp
freezer_actual_temp
flex_zone_actual_temp
refrigerator_setting_temp
freezer_setting_temp
refrigerator_door
freezer_door
door_overtime
energy_consumption
```

源码里还有字节解析：

```text
refrigerator_actual_temp = (body[17] - 100) / 2
refrigerator_setting_temp = body[37]
```

这说明美的的部分型号映射更静态：

```text
先识别 appliance type / model
  ↓
加载对应设备类
  ↓
按固定协议字段解析状态
  ↓
映射成 HA entity
```

这里的源码确实包含“某类设备的属性语义与协议字段”，但只覆盖已经逆向适配的设备类型，并不等于所有美的产品。

## 3 Haier：按地区 App 分成两套社区集成

本地已下载的 16 个插件中没有海尔。

Home Assistant 官方核心当前也没有 `haier` 或 `hon` 集成。海尔主要依靠 HACS 社区集成，并且中国区和海外区使用不同 App，不能混装。

### 3.1 海外 hOn：Andre0512/hon

```text
Andre0512/hon
  当前约 1533 stars
  核验 commit 70eb6c0
  基于 pyhOn
  连接 Haier / Candy / Hoover 的 hOn App
```

项目 README 当前声明支持：

```text
11 类家电
134 个已确认型号
320 个实体
28 种语言
```

其中冰箱已确认 11 个型号。

Haier 品牌：

```text
HDPW5620ANPD
HBW5519ECM
HDW5620CNPK
HFW7720ENMB
HFW7819EWMP
HSW59F18EIPT
HTW5620DNMG
```

Hoover 品牌：

```text
HOCE7620DX
```

Candy 品牌：

```text
CE4T620EB
CCE4T620EWU
CCE4T618EW
```

冰箱暴露的 HA 实体包括：

```text
climate / number
  Fridge
  Freezer
  MyZone

switch
  Auto-Set Mode
  Super Cool
  Super Freeze

button
  Program Start
  Program Stop

select
  Program
  Zone

sensor / binary_sensor
  Temperature Fridge
  Temperature Freezer
  Door Status
  Room Temperature
  Room Humidity
  Holiday Mode
  Errors
```

这说明海尔插件同样采用“固定 appliance model/键位 + 设备实际能力”的映射方式，并不是把所有海尔型号穷举成一张万能表。

### 3.2 中国区 Uhome：banto6/haier

中国区海尔智家使用 Uhome，`Andre0512/hon` 的 README 明确标为不支持。

对应的社区集成：

```text
banto6/haier
  HACS integration
  domain = haier
  version = 1.3.0
  iot_class = cloud_polling
  接入海尔智家 Uhome
```

README 的定位是“理论上支持所有设备”，实际机制不是预置全量型号表：

```text
登录海尔智家
  ↓
获取用户账号下的真实设备与 product_code / product_name
  ↓
请求海尔云端 devdigitalmodels
  ↓
得到该设备的 attributes
  ↓
按 readable / writable / valueRange 动态转成 HA entity
```

它的 `attribute.py` 转换规则包括：

```text
可读且不可写
  → sensor / binary_sensor / select

可写 STEP 数值
  → number

可写 LIST
  → select

可写 bool
  → switch

一次性 boolean command
  → button

满足空调字段组合
  → climate

满足热水器字段组合
  → water_heater

满足 openDegree
  → cover
```

这比固定 product model 表更动态。插件本身不需要知道“某个冰箱的全部实体”，而是根据 Uhome 返回的数字模型生成。

对本地 MCP 的意义：

```text
插件提供属性解释规则
Uhome 数字模型提供该型号的真实属性
HA Entity Registry 提供最终生成结果
```

## 4 Tuya：类别规则 + 云端 DP 定义

Smart Life / Tuya 的核心模型：

```text
设备 category
  ↓
选择该类别对应的 entity description
  ↓
读取设备实际提供的 DPCode
  ↓
按 status_range / function 校验类型和范围
  ↓
映射到 HA entity
```

源码中可以看到：

```text
device.category
device.product_id
device.status
device.status_range
DPCode
```

它的结构介于 Xiaomi 和 Midea 之间：

```text
静态部分
  某 category 有哪些常见 DP、该类别通常生成什么 entity

动态部分
  产品实际上报的 DP、类型、枚举和数值范围
```

因此插件里的 category 描述是规则，用户账号里的设备状态和 DP 定义才是具体设备能力。

## 5 不同插件的典型模式

| 模式 | 代表 | 插件里主要存什么 | 设备实例从哪来 |
|---|---|---|---|
| 规范驱动 | Xiaomi Home | MIoT SPEC 转换规则、型号修补规则 | 小米云账号 + MIoT SPEC |
| 静态协议驱动 | Midea AC LAN | 设备类型、字节协议、固定属性集 | 局域网发现 + 型号 |
| 类别 + 动态字段 | Tuya / Smart Life | category 规则、DPCode 描述 | 云端账号 + DP status/range |
| 云端产品描述 | Haier / hOn | appliance key、控件映射 | hOn 账号 + 产品能力 |
| 云端数字模型 | Haier / Uhome | attribute 类型与 read/write/valueRange 规则 | Uhome 账号 + devdigitalmodels |

共同点：

```text
插件代码提供解释器
真实设备提供实例
厂商协议提供能力描述
HA registry 提供实际存在和启用情况
```

## 6 对“完整设备映射”的正确理解

插件源码里存在的是：

```text
协议映射
字段映射
类别映射
HA entity 映射
少量型号特例
少量支持/不支持型号清单
```

插件源码通常不包含：

```text
所有用户设备实例
所有型号的完整能力表
每个型号所有属性的当前状态
用户实际启用或暴露的实体
```

要形成完整的设备能力索引，必须组合：

```text
插件规则
  +
设备注册表
  +
实体注册表
  +
实体 state / attributes
  +
厂商协议能力
  +
当前暴露配置
```

## 7 对当前米家冰箱案例的意义

```text
Xiaomi Home 插件源码
  定义“可写数值属性通常变 number”
  定义“只读属性通常变 sensor”
  提供少数型号修补

小米云端设备实例 + MIoT SPEC
  决定这台冰箱实际有哪些 service/property/action

HA 实体注册表
  记录最终建出了哪些 entity_id

Assist 暴露配置
  决定哪些实体进入官方 MCP 的工具和上下文
```

因此不能从 Xiaomi 插件源码里直接查到：

```text
“这台 midjd6 冰箱的全部能力”
```

能够查到：

```text
“这类 MIoT 属性会被解释成什么 HA entity”
“该型号是否需要特殊转换”
```

真实设备能力需要从当前 HA 实例读取，或者使用设备的 MIoT SPEC URN 从云端获取原始 SPEC。

## 8 结论

```text
插件源码可以告诉我们映射规则
部分插件也包含静态设备类型和相关字段
Xiaomi Home 对真实米家设备的覆盖主要依赖运行时 MIoT SPEC
它没有把每一种米家冰箱预先写死在插件里
当前冰箱的目标温度、温度、门状态等能力，
来自该设备实际 SPEC 按通用规则转换后的 HA entity
```

因此做跨协议语义建模时，插件源码应当作为“能力解释规则库”使用，真实设备能力则必须从当前 HA 实例和厂商协议描述中抽取。
