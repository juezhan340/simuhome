# 02：协议适配与设备能力——五篇论文怎么做

2026-10-12。起因：担心我们的"六字段 + 八动作"把设备能力框死；
想看看 SimuHome 的 Matter 路线以及另外几篇论文各自怎么处理
「支持/适配协议的能力」与「设备能力」这两个问题。

阅读对象：`0524_4个bench\` 四篇（HomeBench / PersonalHomeBench / SMH-Bench / SimuHome）
与 `0520_方法相关的论文\19_HomeFlow`。英文原文优先；只有中文译本的按中文摘录。
摘录后的行号指对应 txt 文件的行号。

## 1 一屏对比：五种做法

```text
论文            能力从哪来                     执行接口粒度                 协议适配
SimuHome        Matter 标准（端点/集群/属性/命令） 协议级：cluster 命令 + 写属性   真·标准对齐，可迁真机
SMH-Bench       自建声明式 schema（属性/服务）      服务级：device.service(args)    未提（纯仿真）
HomeFlow        自建 YAML 设备规格（属性/服务）      服务级：light.turn_on()        明确说未做：厂商协议适配是未来工作
HomeBench       手工整理 15 类设备的 API 方法       方法级：room.device.method      未提（虚拟平台）
PersonalHomeBench 厂商公开文档（LG/三星）特征级接口   特征级 + Java 家电专用智能体     未提协议；控制沙箱，具身是未来工作

我们（对照）     HA 域 + 角色推断（动态生成）        统一 8 动作：execute_action     由 HA 承担协议适配
```

## 2 SimuHome：把 Matter 标准当成能力底座

### 2.1 协议怎么适配

SimuHome 直接按 Matter 行业标准构建模拟器，"在 SimuHome 中训练和验证的智能体可以在
真正的 Matter 兼容设备上运行，只需极少的调整"（行 84-86）；结尾再次强调
"与 Matter 对齐的模拟器与基准，能够近乎无缝地迁移到真正的 Matter 兼容设备上"（行 639-642）。

### 2.2 设备能力怎么定义

```text
状态   "设备状态由端点、集群和属性组成的 Matter 分层模型表示"（行 160-162）
动作   "动作 at 作为 Matter 命令实现"（行 162）
工具   "这些工具的结构反映了 Matter 在定义设备能力方面的模块化方法"（行 157）
规模   共建模 17 种设备类型（行 150），附录 A.4 给出每种设备类型对应的 Matter 集群
```

附录 A.2 的工具列表就是能力模型本身：13 个工具里包含
`获取设备结构（端点、集群、属性、命令）`、`获取集群文档（在 Matter 集群文档上语义搜索）`、
`执行命令（设备ID/端点ID/集群ID/命令ID/参数）`、`写属性`——
执行接口是协议级的通用形式，不是一张固定动作词表。

系统提示里明确要求运行时学习与验证（行 1231-1234、1249）：

```text
[Matter协议] 层级：设备 -> 端点 -> 集群 -> 属性/命令，使用 API 返回的精确 ID；
当不确定设备能力或集群操作时：用 get_device_structure 探索设备端点和集群；
用 get_cluster_doc 理解集群属性、命令及依赖关系；通过这些发现工具动态学习 Matter 协议。
[工作流调度] 调度前必须准备：验证设备能力和集群；仅使用完全验证的参数进行调度。
```

### 2.3 例子

```text
设备：可调光灯 = 基本信息 + 级别控制 + 开关（A.4 表 5）
动作：命令(设备, 命令) —— 如"打开客厅灯"对应 命令("客厅灯","开启")（行 276）
带时间的任务：调度工作流(时间"2025.09.01 19:00", 步骤=[命令("厨房灯","开启")])（行 267）
```

### 2.4 可扩展性

新设备 = 按 Matter 标准组合已有集群（或补一个标准集群实现）；
智能体不需要预先背下所有设备，靠"设备结构 + 集群文档"两个发现工具现场学。
扩展方向由行业标准给出，模拟器与真机同构。

## 3 SMH-Bench：声明式 schema，能力即数据

### 3.1 协议怎么适配

全文没有 Matter/协议/硬件层的讨论——HomeEnv 是纯仿真环境，
"提供结构化的家庭状态、可配置的设备抽象与标准化的查询/控制接口"（行 183-186）。

### 3.2 设备能力怎么定义

能力写在 schema 里，是数据不是代码：

```text
Home = rooms + devices；device 字段：
  name / description / attributes / services / components / userdata
userdata：did、spid（相同能力 schema 的设备共享的产品规格 ID）、
          category、subcategory、tags、room（表 6、表 7）
attributes：name/description/type/value/range/options/items/precision/unit（表 9）
services：name/description/arguments/code（状态转移规则）；
          调用前校验名称、类型、范围、精度、枚举，非法调用不改状态（A.5）
多部件设备：用 components 命名空间，如 fan-light 的 light.* 与 fan.*（A.6）
```

覆盖 12 个设备大类（light / sensor / fan_light / media / ac / vacuum /
water_heater / lock / cover / fan / washing_machine / oven，表 8）。
代表性服务（表 12）：`turn_on/off`、`set_brightness`、`set_color_temperature`、
`set_ac_mode`、`set_target_temperature`、`set_speed_level`、窗帘 `open/close/set_position`、
音箱 `play/pause/stop`、扫地机 `start/pause/return_to_base`、门锁 `lock/open`。

任务形式：单动作 `a = [device.service(args)]`（行 150-151）；
环境执行前检查"操作是否存在、参数是否满足类型/范围/枚举约束"（行 235）。

### 3.3 例子

```text
light：light.state、light.brightness、light.turn_on、light.set_brightness(1~100)（行 1416-1422）
门锁：lock / open；扫地机：start / pause / return_to_base（表 12）
```

### 3.4 可扩展性

加设备 = 加一条 spec（同能力 schema 复用 spid）+ 提供 attributes/services 列表；
多部件设备用 components 拆命名空间。没有行业标准背书，扩展自由度大、
但与真机是否一致不做承诺。

## 4 HomeFlow：同一套 YAML 规格 + 明确承认协议适配没做

### 4.1 协议怎么适配

局限章节写得很直白（行 490-494）：

```text
"目前 HomeFlow 依赖确定性仿真，需要 sim-to-real 适配以处理真实世界的不确定性；
更广的部署还需要适配各种厂商专有协议来扩大设备覆盖"（行 490-493）
```

也就是说：厂商协议适配被明确列为"未来工作"，不是它已经解决的能力。

### 4.2 设备能力怎么定义

设备是 YAML 规格：属性（type/range/unit）+ 服务（name/arguments/code 状态转移），
例如 light 的 `turn_on / turn_off / set_brightness(1~100) / set_hs_color`（附录 A.1）。
交互走统一高层 API（附录 A.2）：

```python
entities = Entity.load(f); light = light_spec.rand()
light.turn_on(); light.set_brightness(80)
```

动作空间是异构的：`A = A_NL ∪ A_Exec`，`A_Exec` 可以是"生成 Python 代码片段或 API 调用"（行 120-131）。
Blueprint 元信息里列了两类接口：device APIs（如 `light.turn_on`、`ac.set_temp`）
与 tool APIs（如 calculator、weather）（行 771-780）。
系统提示还要求"控制前必须抓取设备能力、校验参数"（行 1071-1085）。

### 4.3 例子与可扩展性

```text
例子：device("1001").set_brightness(80)（A.3 的 Gym 环境示例）
扩展：同 SMH 的 schema 路线；协议扩展被列为未来工作
```

## 5 HomeBench：手工整理的 15 类设备方法集

### 5.1 协议怎么适配

没有真实协议："考虑到市场上访问智能家居开发环境的挑战，我们采用了虚拟智能家居设置"
（行 458）；"收集了 15 种常用的智能家居设备，并为每种设备识别了可通过智能家居平台
调用的 API 方法…用 Python 类实现…简化部分设备的方法，仅保留核心功能，并为其他设备
随机添加额外方法"（行 462-470）。

### 5.2 设备能力怎么定义

任务定义即能力模型（行 307-316）：

```text
每个设备 dj 有：可操作属性的状态 s、一组可调用方法 M = {m1, m2, ...} 与参数；
模型输出 h, u → [ri.dj.mk]（房间.设备.方法），无效指令输出 错误_输入。
```

数据质量检查里有"语义对齐（指令与设备/房间能力对比）"与"动作一致性"
（行 493-494）——无效指令主要来自"设备不存在"或"方法不存在"。

### 5.3 例子（附录表 7 的方法清单）

```text
灯光设备   打开/关闭/设置亮度/设置颜色
空调设备   打开/关闭/设置温度/设置模式/设置风扇速度/设置摆动
风扇设备   打开/关闭/设置速度/设置摆动
窗帘设备   打开/关闭/设置开合度；百叶窗 打开/关闭；车库门 打开/关闭
热水器/空气净化器/加湿器/除湿器/香薰/媒体播放器/扫地机器人/垃圾桶（pack）…

机器指令示例：{instruction: set_intensity(30), device: humidifier, room: guest_bedroom}
→ 人类指令："将客房中加湿器的强度提高2%"
```

### 5.4 可扩展性

未讨论。能力集是研究者按 15 类设备手工整理的，设备池随机组合、方法可随机增删，
但没有"接入新协议/新品牌"的机制。

## 6 PersonalHomeBench：按厂商公开文档做"特征级接口"

### 6.1 协议怎么适配

不涉及通信协议；它的"适配"发生在工具层：
"我们基于主要智能家居供应商的公开文档，为超过 40 种智能家电实现了特征级接口，
构建了一个全面的控制沙箱"（脚注：LG 电子和三星）（行 288-292）。
设备交互"可以是确定性的（如电源控制），或由家电专用智能体进行中介
（如为冰箱配备的个性化菜谱推荐器）"（行 291-294）。

### 6.2 设备能力怎么定义与使用

```text
PersonalHomeTools：结构化家庭信息检索 + 持久记忆与事件 + 环境感知 + 真实设备控制（行 94-96）
特征推荐（FR）：智能体根据"API 级清单"按上下文相关性对家电特征排序（行 243-245）
计划生成（PG）：生成结构化多步计划，协调异构设备（例如安全事件 → 启动应急、
              通知看护者、关闭危险家电）（行 245-250）
```

### 6.3 可扩展性与边界

覆盖广度靠"厂商文档 + 特征级接口"堆出来（40+ 家电）；
局限章节明确："专注于非具身智能家居辅助，扩展到混合具身-设备设置是未来工作"（行 899）。
没有统一能力词汇表，FR 任务本身就是"让模型在特征清单里挑"。

## 7 汇总观察

```text
① 真正把"协议标准"吃进能力模型的只有 SimuHome——
   能力=标准集群组合，执行=协议命令，发现=设备结构+集群文档，扩展=跟标准。
② SMH-Bench / HomeFlow 是"schema 派"：能力=数据（属性+服务+组件），
   扩展=加 spec；不与任何真机标准绑定。HomeFlow 自己承认厂商协议适配尚未做。
③ HomeBench 是"手工词表派"：15 类设备的方法集写死，换取可控与简洁；
   和我们的八动作最接近，但它连"按设备动态生成"都没有。
④ PersonalHomeBench 是"覆盖派"：用厂商文档摊大饼，特征级、无统一词汇表，
   重个性化与主动性，协议/具身都不在其范围。
⑤ 我们的现状：动作词表封闭（8 个），但设备能力是动态生成的
   （按角色推 actions、范围取设备自报值、冰箱能拆成两台）——
   比 HomeBench 活，比 SMH/SimuHome 死；协议适配由 HA 承担，不在我们层里。
```

## 8 对我们的含义（供讨论）

担心"被限定死"是成立的：现在新增一类能力（比如扫地机 start/pause/return_to_base、
门锁 lock/open、音箱 play/pause）必须改词表 + 改映射代码。
但五篇里只有 SimuHome 真正解决了这个问题，而且它的解法依赖两个前提：
Matter 是行业标准（能力词表不用自己造）+ 智能体带文档检索工具（能现场学）。

我们如果要往"不死"的方向走，大致有三条路，可组合：

```text
A 保持八动作最小表面，增加"能力扩展注册表"：
  核心 8 个稳定；新能力按 <domain, device_class> → 规范动作注册，
  execute_action 的入参形态不变；模型侧只看到设备真正拥有的动作。
B 借力 HA：inspect_device 已经把设备自报的 actions 返回给模型。
  扩展点是"从 HA 服务清单自动映射规范动作"，映射不到的按规则透传
  （类似 SMH 的 service 透传），把"新增设备"变成"配置 + 映射表"而不是改核心代码。
C 学 SimuHome 的发现链路：给模型一个"能力文档/清单"查询（或让 inspect_device
  返回能力说明），让它运行时确认能力再执行——但这条要小心端侧小模型的上下文预算。
```

一句话：SimuHome 值得借鉴的不是某个动作名，而是"标准驱动的能力来源 +
运行时能力发现 + 执行接口与标准对齐"这三件套；我们已经有其中的"动态生成"骨架，
缺的是"词表可扩展"的规则和"能力来源不只靠我们手写"的机制。
