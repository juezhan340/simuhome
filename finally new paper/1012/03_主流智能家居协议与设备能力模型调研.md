## 1 一屏：协议全景与分层

先把混在一起的概念拆开——**"传输/组网"和"设备能力"常常不是同一层**：

```text
能力层（设备功能怎么被定义与展现）
  Matter 设备类型+集群 | Zigbee ZCL 集群 | Z-Wave 命令类(CC) |
  KNX 组对象+数据点类型(DPT) | BLE Mesh 模型 | （Wi-Fi 设备：厂商私有/云 API）
      ↑ 有的协议自带能力层（Matter/Zigbee/Z-Wave/KNX/BLE Mesh），
        有的只有传输层（Thread/Wi-Fi），能力来自别处
传输层
  Thread | Zigbee(NWK) | Z-Wave | Wi-Fi | BLE | KNX 总线 | RS-485 | LoRa
物理网络
  802.15.4 | 2.4G/5G | Sub-G(868/908/433M) | 双绞线 | 红外 | ...
```

```text
协议        层面          能力模型                   主要阵营/场景            占比位置（定性）
Matter     应用层(传输无关) 设备类型+集群+属性/命令       苹果/谷歌/亚马逊/三星等  增长期，软件更新在铺
Zigbee     应用层+网络       ZCL 集群+设备类型             Hue/Aqara/米家多模网关    网关子网主力
Z-Wave     应用层+网络       命令类(CC)                  北美安防/全屋             北美为主，全球较小
Thread     网络层（IP Mesh） 不定义能力（靠 Matter 等）     苹果/谷歌/亚马逊路由器     增长期，随 Matter 走
Wi-Fi      传输层           厂商自定义（云/局域网）        几乎全部联网家电/摄像头    消费级数量最大头
蓝牙/BLE   传输层+组网       GATT 服务 / Mesh 模型        配网、灯、传感器、锁       配网通道几乎全覆盖
KNX        应用层+总线       组对象+DPT                  楼宇/高端住宅             高端固定，计量小
Modbus     应用层(工控)      寄存器表（厂商定义）          暖通/采集/网关            细分
```

## 2 逐个协议：能力如何被约束、如何被展现

### 2.1 Matter：用"设备类型 + 集群"把能力标准化

能力结构是一棵固定的树：**Node → Endpoint → Cluster → Attribute / Command / Event**。
SimuHome 论文的评测提示词把这个结构写得很直白："设备属性遵循格式 '端点.集群.属性'，
例如 '1.OnOff.OnOff' 表示端点 1 的 OnOff 集群的 OnOff 属性"（证据见 1012\02 文档 §2）。

约束方式是**认证**：Matter 官方手册明确写"要认证一台 Matter 设备，必须符合某一个
已批准的设备类型；截至 Matter 1.4，可认证类型包括……"（handbook.buildwithmatter.com）。
设备类型直接对应能力清单，例如：

```text
照明      On/Off Light、Dimmable Light、Color Temperature Light、Extended Color Light
插座      Smart Plugs/Outlets
暖通      Thermostat、Fan
门/遮阳   Door Lock、Door Lock Controller、Window Covering、Window Covering Controller
机器人    Robotic Vacuum Cleaner
影音      Speaker、Video Player、Casting Video Client…
工具类    Root Node、Power Source、OTA Requestor/Provider、Bridged Node…
```

"展现"方式：控制器读取集群属性、下发集群命令（如 On/Off 集群的 On/Off/Toggle；
Level Control 的 MoveToLevel；Thermostat 的设定点），行为跨品牌一致。Matter 与传输解耦，
可跑在 Wi-Fi / Thread / 以太网之上。

### 2.2 Zigbee：ZCL 集群是能力单元，靠网关展现

Zigbee 的能力层叫 ZCL（Zigbee Cluster Library）：**集群（cluster）= 一类功能**，
每个集群带若干属性（attributes）和命令（commands）；设备类型决定"应该实现哪些集群"。
CSA 官方对它的描述是 "Rich data model provides a universal language for devices to
work together, regardless of brand"（csa-iot.org Zigbee 页）。

```text
典型集群（通用知识 + CSA 资料）：
  0x0006 On/Off        命令 Off / On / Toggle
  0x0008 Level Control 命令 MoveToLevel / Step / Stop（调光、档位）
  0x0300 Color Control 色温/颜色
  0x0201 Thermostat    设定点、模式
```

实际工程里的"展现"靠网关翻译。zigbee2mqtt 的文档写得很清楚：
"Zigbee2MQTT exposes the device capabilities through the exposes property"
——每台设备被翻译成一份能力清单（exposes，含 binary/numeric/specific 等类型）。
所以终端用户看到的"设备能力"其实是**设备自报 + 网关定义文件**共同决定的结果。
Zigbee 定位低功耗 Mesh，照明、传感器、窗帘是主力场景，几乎都要网关（米家多模、Hue、Aqara…）。

### 2.3 Z-Wave：命令类（Command Class）决定一切

Z-Wave 的能力单元是 **Command Class（CC）**：设备在配网时声明支持哪些 CC，
控制器通过对应的 CC 命令控制。官网导航里直接列着 "Developer Specifications" 与
"Command Classes" 两个入口（z-wavealliance.org；该子页本次抓取被 403 拦截）。

```text
常见 CC（通用知识，名称按官方规范）：
  Binary Switch CC         开/关
  Multilevel Switch CC     调光/档位（百分比）
  Thermostat Setpoint CC   目标温度
  Notification CC          报警/事件
  Central Scene CC         场景按键
```

特点：Sub-GHz 频段、Mesh、Z-Wave Plus 认证 + S2 安全；市场集中在北美家用安防/全屋，
全球份额较小。

### 2.4 Thread：只是网络层，不定义设备能力

Thread Group 官方描述："Thread was designed with one goal in mind: to create the best way
to connect and control products in the home and buildings"，"Built-in security at the
network layer"，"based on the power-efficient IEEE 802.15.4 MAC/PHY"
（threadgroup.org What is Thread）。

它提供的是 **IPv6 Mesh 网络**（6LoWPAN + 802.15.4），设备能力由应用层定义——
今天事实上就是 Matter；Thread Border Router 负责接入 IP 网络（很多智能音箱/路由器内置）。
**结论：讨论"能力模型"时不要把 Thread 和 Zigbee/Matter 并列**，它和 Wi-Fi 一样是"管子"。

### 2.5 Wi-Fi：没有统一能力层，能力=厂商私有

Wi-Fi 只是联网管道：设备功能怎么暴露完全由厂商决定——云 API、局域网协议、MQTT、
或靠 Home Assistant 集成插件翻译。优点是**不需要网关、芯片成本被家电主控摊平**，
所以中国市场的联网家电（空调、冰箱、洗衣机、摄像头、插座）绝大多数是 Wi-Fi。
代价是没有统一语义、每家一套，这正是 Matter over Wi-Fi 想补的洞。

### 2.6 蓝牙 / BLE Mesh：配网通道 + 低功耗子网

```text
BLE（点对点）  GATT 服务/特征（SIG 定义一部分，厂商私有占大头）
BLE Mesh      "模型"作为能力单元（Generic OnOff、Light Lightness、Sensor 等 SIG 模型
              + 厂商自定义模型），2017 年发布，多对多组网
```

两条主要用途：① 设备配网/近场控制（几乎所有 Wi-Fi/Zigbee 设备都带 BLE 配网）；
② 低功耗子网（灯具、开关、传感器、门锁），智能音箱常兼做 Mesh 网关
（中文技术文章普遍持此判断，见 CSDN"蓝牙 Mesh 智能家居生态圈"等）。

### 2.7 KNX：组对象 + DPT 的楼宇标准

KNX 是欧洲起源的**总线系统**（也有 KNX RF/IP 形态），能力单元是
**组对象（group object）+ 数据点类型（DPT, datapoint type）**：每个组对象声明自己
是什么 DPT（例：1.001 开关、5.001 百分比、9.001 温度——DPT 编号为通用知识），
工程侧用 ETS 配置。官网结构（认证设备、灯光/HVAC/遮阳/能源/安防/场景等目录）显示其
应用重心在楼宇与高端住宅自动化（knx.org；DPT 支持页本次 403）。

### 2.8 Modbus / RS-485：寄存器表就是能力表

工控体系没有"设备类型"概念：能力=厂商的**寄存器表**（coil / discrete input /
holding register / input register）。地暖、新风、电表、网关常用它接进智能家居；
因为没有自描述，Home Assistant 里要手工写 modbus 映射。HA 的 modbus 集成是这条路线的
标准做法（modbus.org 本次 403，寄存器模型为通用知识）。

### 2.9 边缘与补充

```text
433MHz / 红外   存量遥控设备：单向、无状态回读，靠学习码/红外码
LoRa / NB-IoT   广域低功耗：水表电表、户外场景，家居控制边缘
PLC（电力线）    小规模存在，主要用于替代布线的子场景
```

## 4 横向对比：能力单元 / 标准程度 / 发现与扩展方式

```text
协议       能力单元             标准程度       设备能力怎么被发现            扩展新设备的方式
Matter    设备类型+集群+属性/命令 开放标准(认证) 读集群定义/属性；认证库       按标准实现设备类型→认证
Zigbee    ZCL 集群+属性/命令     开放标准(认证) 网关暴露 exposes 列表         实现/引用集群，做网关定义
Z-Wave    命令类 CC             开放标准(认证) 配网声明支持的 CC 集          实现 CC 集，认证
Thread    无（网络层）           开放标准        ——（能力看上层，通常是 Matter）——
Wi-Fi     厂商私有 API/协议      无标准         厂商云/局域网/HA 集成         每家一套，或套 Matter
BLE Mesh  模型(Model)            SIG 标准+私有   模型清单（composition data）  实现 SIG/私有模型
KNX       组对象+DPT            开放标准(认证)  ETS 工程文件                  ETS 配置设备
Modbus    寄存器表              事实标准(无认证) 厂商文档/寄存器表              手工映射
```

一句话总结各协议的"约束力"：

```text
约束最强   Matter / KNX：设备类型（或组对象）与强制能力集写在标准里，认证兜底
中等       Zigbee / Z-Wave / BLE Mesh：标准集群/命令类/模型 + 厂商自定义空间
最弱       Wi-Fi 私有、Modbus：能力=厂商文档，谁家的设备谁定义
```

## 5 对我们的含义

```text
① 我们的位置：协议适配这件事实际由 Home Assistant 承担——Zigbee/Z-Wave/Thread/Matter/
   KNX/Modbus 都被 HA 集成抽象成 entity + service；我们的 claim/roles/actions 建在
   HA 域（switch/light/fan/climate/cover/select/number）之上，是"再上一层"的语义收敛。
② 六字段八动作 ↔ 各协议词汇的对应（举例）：
     Matter Dimmable Light(OnOff+LevelControl) → HA light → power+level → 3+set_brightness
     Matter Thermostat                          → HA climate → power/mode/target/current → 5 动作
     Zigbee On/Off cluster / Z-Wave Binary Switch CC → switch → 3 动作
     KNX DPT 1.001 / BLE Mesh Generic OnOff      → 开关/灯 → 3 动作
     Modbus 寄存器（地暖设定值）                   → number → 1 动作
③ 协议标准里"比我们宽"的词汇，随时可以借：Matter 的设备类型表（Vacuum/Lock/Window
   Covering/Speaker…）、Zigbee 集群、Z-Wave CC、BLE Mesh 模型。也就是说，02 文档里
   讨论的"八动作扩展注册表"不需要拍脑袋命名——直接对齐 Matter/Zigbee 的标准词表即可。
④ 如果要在论文/产品里讲"协议适配能力"：最站得住的路线仍是"HA 之上做统一语义 +
   对齐 Matter 词表"（与 SimuHome 的选择同源）；自建一套私有设备类型体系（SMH/HomeFlow
   路线）拓展自由但不可迁移真机，HomeFlow 自己把厂商协议适配列为未来工作。
```
