# 01：模型可见的接口面与完整交互样例

2026-10-12。依据 `ha_mcp_universal` 当前代码（契约 `contract\tools.py`、协议壳 `server.py`、
8 个工具实现）与实测记录整理。目的：把"小模型实际看到、收到什么"逐字列清楚，
再用完整样例展示模型在每一步是怎么做的。

开头先给设备能力现状（支持哪些设备类型、每类多少功能、我们怎么做的），
后面再逐字列模型可见的接口面与完整交互样例。

## 1 设备能力现状（先读这个）

### 1.1 一句话

设备能力被归一成"六字段 + 八动作"：每台设备能用哪些动作、参数范围是多少，
由服务端按角色实时生成（范围取设备自报值），模型只通过 `inspect_device.actions[]` 感知。
当前部署（4 房间 14 台设备）合计 **43 个可执行动作位**：

```text
9 个开关 × 3 + 2 台空调 × 5 + 1 台风扇 × 4 + 冰箱拆 2 台 × 1 = 43
```

### 1.2 统一词汇表

```text
六状态字段   on / mode / target / level / position / current
八个动作     turn_on / turn_off / toggle / set_mode / set_temperature /
            set_percentage / set_brightness / set_position

动作与回读字段   turn_on / turn_off / toggle      → 回读 on
                set_mode                          → 回读 mode
                set_temperature                   → 回读 target
                set_percentage / set_brightness   → 回读 level
                set_position                      → 回读 position
```

### 1.3 设备类型 → 能力矩阵（当前实现的完整覆盖面）

```text
HA 域      角色                    动作数  动作清单（参数范围来源）
switch     power                   3       turn_on / turn_off / toggle
light      power (+level)          3~4     3 + set_brightness（0~100）
fan        power (+level)          3~4     3 + set_percentage（0~100，步长自报）
climate    power/mode/target/current  5    3 + set_mode（枚举自报）
                                            + set_temperature（范围自报）
cover      position                1       set_position（0~100）
select     mode                    1       set_mode（选项自报）
number     target 或 level         1       set_temperature 或 set_percentage（范围自报）
sensor     current（温度）          0       只读；纯传感器不进设备清单，只供环境量
```

注：当前部署里没有 light / cover / select 实体（沙盒的灯是 switch 域），
这几类能力在代码里已实现，对应实体接进来即自动生效。

具体一点，沙盒空调 `living_room_ac` 的 `inspect_device.actions` 实测是 5 条：

```json
[
 {"action": "turn_on",  "description": "打开空调", "params": {}},
 {"action": "turn_off", "description": "关闭空调", "params": {}},
 {"action": "toggle",   "description": "在当前状态上取反", "params": {}},
 {"action": "set_mode", "description": "切换模式",
  "params": {"mode": {"type": "string", "enum": ["off", "cool", "heat"]}}},
 {"action": "set_temperature", "description": "设定目标温度",
  "params": {"value": {"type": "number", "minimum": 7.0, "maximum": 32.0, "step": 0.5}}}
]
```

冰箱是米家的 number 实体：冷藏 / 冷冻各拆成一台设备，各暴露 1 个动作
（`set_temperature`，范围来自设备自报）。这就是"每类设备支持多少功能"的直观口径。

### 1.4 我们目前怎么做的（机制）

```text
claim → roles → actions → 校验执行

① claim   实体按平台规则认领：沙盒 = MQTT discovery 的 simuhome_* 实体；
          米家 = xiaomi_home 平台实体
② roles   按 domain + device_class + 单位推六个角色：
            switch / light / fan → power（light 带亮度、fan 带档位时再加 level）；
            climate 一肩四角色（power / mode / target / current）；
            cover → position；select → mode；
            number 按单位与区间归 target（温度）或 level（0~100）
③ 拆分    同一角色出现多值（冰箱冷藏/冷冻、多路同角色实体）按方位词拆成多台逻辑设备；
          整机共享角色挂第一台；只有只读角色的设备不进设备清单
④ actions 按角色生成动作清单；枚举与 min/max/step 全部取设备自报属性
⑤ 执行    四道闸门本地校验 → 映射到 HA 服务 → 回读验证（verified）；
          不支持的动作为 UNSUPPORTED_ACTION，参数越界为 BAD_REQUEST（都不发给后端）
```

粒度说明：刻意粗。不把 HA 每个域的每个服务都暴露，而是压到 8 个动作；
新设备优先归入已有动作，确实不属于才扩展词表（统一粒度口径见双仓库 11 号《最终设计》
与 12 号《统一能力接口设计》）。

## 2 一屏：模型看到的东西只有两样

```text
① tools/list —— 8 个工具，每条只有三个字段：
     name / description / inputSchema（参数的 JSON Schema）

② 每次 tools/call 的返回值 —— 统一外壳：
     成功  {"ok": true,  "data": {...}, "error": null}
     失败  {"ok": false, "data": null, "error": {code, message, hint}}

看不到（全部留在服务端）：
  meta{elapsed_ms, clock}、契约里的 returns / errors 字段、
  内部状态机、sqlite、审计行、claim 规则、别名文件、日志、重试与回读细节
```

顺序即 `config.yaml` 的 `tools.expose` 白名单顺序：
`observe_home → inspect_room → inspect_device → execute_action → finish → inspect_time → time_control → memory`。
这些工具背后能操作什么设备、每台设备支持多少功能，先看 §1。

## 3 tools/list 逐字清单

下面每段就是模型在 `tools/list` 里收到的内容（wire JSON 的 name / description / inputSchema），
另用一行给出"调用一次会拿到什么"（这一行在契约里，但不对模型下发）。

### 3.1 observe_home

```json
{
  "name": "observe_home",
  "description": "全屋快照：房间清单、每房间环境量、当前时间",
  "inputSchema": {"type": "object", "properties": {}}
}
```

调用一次拿到：`rooms{room_id: {name, env{4 环境量}, devices[]}} + time + clock + counts{rooms, devices, metrics}`。

### 3.2 inspect_room

```json
{
  "name": "inspect_room",
  "description": "读一个房间：环境量、设备清单、门状态（当前恒为 null）",
  "inputSchema": {
    "type": "object",
    "properties": {"room_id": {"type": "string", "description": "房间 id，如 living_room"}},
    "required": ["room_id"]
  }
}
```

调用一次拿到：`{room_id, name, env{}, devices[{device_id, display_name, kind, device_type}], doors: null}`。

### 3.3 inspect_device

```json
{
  "name": "inspect_device",
  "description": "读一台设备：当前状态与可用动作、参数范围",
  "inputSchema": {
    "type": "object",
    "properties": {"device_id": {"type": "string", "description": "设备 id，如 living_room_ac"}},
    "required": ["device_id"]
  }
}
```

调用一次拿到：`{device_id, entity_id, area_id, kind, state{六字段}, actions[{action, description, params{范围}}]}`。
`actions` 是模型选动作与参数的唯一依据。

### 3.4 execute_action

```json
{
  "name": "execute_action",
  "description": "执行一次设备动作：规范动作名 + 参数，执行后回读状态",
  "inputSchema": {
    "type": "object",
    "properties": {
      "device_id": {"type": "string", "description": "设备 id"},
      "action": {"type": "string", "description": "规范动作名，如 set_temperature"},
      "params": {
        "type": "object",
        "description": "动作参数，如 {value: 25.0}",
        "properties": {"value": {"type": "number", "description": "动作参数值，温度写摄氏度、档位写 0~100"}},
        "additionalProperties": true
      }
    },
    "required": ["device_id", "action"]
  }
}
```

调用一次拿到：`{device_id, action, params, state_after{}, state_diff{}, changed, steps[], verified, elapsed_ms}`。

### 3.5 finish

```json
{
  "name": "finish",
  "description": "结束本轮任务：声明完成或拒绝（协议工具，不操作设备）",
  "inputSchema": {
    "type": "object",
    "properties": {
      "outcome": {"type": "string", "description": "结果：completed 或 refused", "enum": ["completed", "refused"]},
      "reason_code": {"type": "string", "description": "refused 用：拒绝原因", "enum": ["OUT_OF_SAFE_RANGE", "READ_ONLY_DEVICE"]},
      "summary": {"type": "string", "description": "一句话说明，可选"}
    },
    "required": ["outcome"]
  }
}
```

调用一次拿到：`{accepted: true, outcome, reason_code, summary}`。

### 3.6 inspect_time

```json
{
  "name": "inspect_time",
  "description": "读当前时间：家庭时区的分钟级时刻与时钟类型",
  "inputSchema": {"type": "object", "properties": {}}
}
```

调用一次拿到：`{now: "YYYY-MM-DD HH:MM", clock: "real|virtual"}`。

### 3.7 time_control

```json
{
  "name": "time_control",
  "description": "一次性预约：schedule 写单 / list 查未执行的单 / cancel 取消",
  "inputSchema": {
    "type": "object",
    "properties": {
      "op": {"type": "string", "description": "操作", "enum": ["schedule", "list", "cancel"]},
      "at": {"type": "string", "description": "schedule 用：YYYY-MM-DD HH:MM（家庭时区）"},
      "steps": {
        "type": "array",
        "description": "schedule 用：1~8 条动作调用",
        "items": {
          "type": "object",
          "properties": {
            "device_id": {"type": "string", "description": "设备 id"},
            "action": {"type": "string", "description": "规范动作名"},
            "params": {"type": "object", "description": "动作参数，如 {value: 26}"}
          },
          "required": ["device_id", "action"]
        }
      },
      "schedule_id": {"type": "string", "description": "cancel 用：schedule 返回的单号"}
    },
    "required": ["op"]
  }
}
```

调用一次拿到：
`schedule → {schedule_id, at, status: "pending"}`；
`list → {now, items[{schedule_id, at}]}`（只含还没执行的单，取消/执行完的不出现）；
`cancel → {schedule_id, status: "cancelled"}`。

### 3.8 memory

```json
{
  "name": "memory",
  "description": "长期记忆读写：整段文本，read 返回原文，write 整段替换",
  "inputSchema": {
    "type": "object",
    "properties": {
      "op": {"type": "string", "description": "操作，默认 read", "enum": ["read", "write"]},
      "text": {"type": "string", "description": "write 用：完整记忆文本；read 不要带"}
    }
  }
}
```

调用一次拿到：`read → {text}`；`write → {"code": "OK"}`。

## 4 返回外壳

成功（`execute_action` 打开电视机的原样返回）：

```json
{"ok": true, "data": {
  "device_id": "living_room_tv", "action": "turn_on", "params": {},
  "state_after": {"on": true},
  "state_diff": {"on": {"from": false, "to": true}},
  "changed": true,
  "steps": [{"target": "switch.simuhome_living_room_tv", "service": "switch.turn_on", "data": {}}],
  "verified": true, "elapsed_ms": 10},
 "error": null}
```

失败（对不存在的设备调用 `inspect_device`）：

```json
{"ok": false, "data": null,
 "error": {"code": "UNKNOWN_DEVICE", "message": "没有这台设备：ghost",
           "hint": "可选设备：['kitchen_fan', 'living_room_ac', 'living_room_tv']"}}
```

规则：`ok=false` 时协议层同时把 `isError=true`；`hint` 是给模型纠错的可用值提示。
`meta{elapsed_ms, clock}` 只写服务端日志，不下发。

## 5 完整样例：模型怎么做

样例取自离线夹具（`tests\fake_ha.py`，与真机返回同形状；个别时间字段是夹具值）。
每步都给出模型发出的 arguments 和收到的完整返回。

### 样例 1：立即控制（打开客厅电视）

发给模型的任务：`把客厅电视打开，然后结束任务。`

```text
[第1步] 模型不确定当前状态 → 先查设备
调用 inspect_device {"device_id": "living_room_tv"}
→ {"ok": true, "data": {
     "device_id": "living_room_tv", "entity_id": "switch.simuhome_living_room_tv",
     "area_id": "living_room", "kind": "switch",
     "state": {"on": false},
     "actions": [
       {"action": "turn_on",  "description": "打开设备", "params": {}},
       {"action": "turn_off", "description": "关闭设备", "params": {}},
       {"action": "toggle",   "description": "在当前状态上取反", "params": {}}]},
   "error": null}

[第2步] state.on=false，且 actions 里支持 turn_on → 执行
调用 execute_action {"device_id": "living_room_tv", "action": "turn_on"}
→ 见 §4 成功外壳：state_after.on=true、changed=true、verified=true

[第3步] 任务完成 → 结束协议
调用 finish {"outcome": "completed", "summary": "已打开客厅电视"}
→ {"ok": true, "data": {"accepted": true, "outcome": "completed",
                        "reason_code": null, "summary": "已打开客厅电视"}, "error": null}

[最终答复] "客厅电视已打开。"
```

模型视角的决策链：`state.on` 决定要不要动手 → `actions[]` 决定用哪个动作 →
`verified=true` 决定可以宣布成功。全程不需要知道背后是 HA 还是别的后端。

### 样例 2：先全屋、再局部（查询）

```text
任务：看一下家里现在什么情况，客厅有哪些设备。

[第1步] observe_home {}
→ {"ok": true, "data": {
     "rooms": {
       "living_room": {"name": "living_room",
                       "env": {"temperature": 26, "humidity": 45, "illuminance": 800, "pm10": 25},
                       "devices": ["living_room_ac", "living_room_tv"]},
       "kitchen":      {"name": "kitchen", "env": {}, "devices": ["kitchen_fan"]},
       "utility_room": {"name": "utility_room", "env": {}, "devices": []}},
     "time": "2025-08-24 08:30:34", "clock": "virtual",
     "counts": {"rooms": 3, "devices": 3, "metrics": ["humidity", "illuminance", "pm10", "temperature"]}},
   "error": null}

[第2步] 缩小到客厅
调用 inspect_room {"room_id": "living_room"}
→ {"ok": true, "data": {
     "room_id": "living_room", "name": "living_room",
     "env": {"temperature": 26, "humidity": 45, "illuminance": 800, "pm10": 25},
     "devices": [
       {"device_id": "living_room_ac", "display_name": "Air Conditioner", "kind": "climate", "device_type": "climate"},
       {"device_id": "living_room_tv", "display_name": "TV", "kind": "switch", "device_type": "switch"}],
     "doors": null},
   "error": null}

[最终答复] "家里共 3 个房间；客厅 26°C、湿度 45%，有两台设备：空调和电视。"
```

### 样例 3：记忆读写

```text
任务：记住"用户喜欢22度"，再读出来确认。

[第1步] memory {"op": "write", "text": "用户喜欢22度"}
→ {"ok": true, "data": {"code": "OK"}, "error": null}

[第2步] memory {"op": "read"}          （op 可省略，默认就是 read）
→ {"ok": true, "data": {"text": "用户喜欢22度"}, "error": null}

[最终答复] "已记住并在读回时确认一致。"
```

### 样例 4：预约——写单 → 查单 → 取消 → 再查

```text
任务：明天早上 7 点把灯关掉；写好后先确认它在列表里，再取消并确认消失。

[第1步] inspect_time {}
→ {"ok": true, "data": {"now": "2026-10-12 21:10", "clock": "real"}, "error": null}
   （模型用 now 推算绝对时间，本样例把 at 定为 +2 分钟）

[第2步] time_control {"op": "schedule", "at": "2026-10-12 21:12",
                      "steps": [{"device_id": "living_room_tv", "action": "turn_off"}]}
→ {"ok": true, "data": {"schedule_id": "sch_917851b6", "at": "2026-10-12 21:12",
                        "status": "pending"}, "error": null}

[第3步] time_control {"op": "list"}
→ {"ok": true, "data": {"now": "2026-10-12 21:10",
                        "items": [{"schedule_id": "sch_917851b6", "at": "2026-10-12 21:12"}]},
   "error": null}

[第4步] time_control {"op": "cancel", "schedule_id": "sch_917851b6"}
→ {"ok": true, "data": {"schedule_id": "sch_917851b6", "status": "cancelled"}, "error": null}

[第5步] time_control {"op": "list"}     （再查一次）
→ {"ok": true, "data": {"now": "2026-10-12 21:10", "items": []}, "error": null}

[最终答复] "已预约、确认在列表里，随后取消并确认列表已清空。"
```

关于"到点执行"：2026-10-09 真机回归做过一次——19:58 建单（`at=19:59` 开灯）→
到点灯确实打开、该单同时从 list 消失 → 随后还原灯状态。

## 6 模型看不到什么（边界）

```text
返回外壳里的 meta           只写服务端日志（elapsed_ms / 契约 clock）
契约 returns / errors       服务端对齐用，不进 tools/list
内部状态                    预约的内部五态（pending/running/completed/failed/cancelled）
                            只影响"什么该显示"；模型侧 list 只有未执行的单
存储与规则                  sqlite、审计行、claim 规则、别名文件、重试与回读细节
隐藏工具                    check_goal / query_events 不在 tools/list；
                            直接调用会得到 BAD_REQUEST「工具当前未开放」
```
